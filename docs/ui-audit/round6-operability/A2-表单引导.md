## 一、结论摘要

### 规模盘点（机械统计，引号内为脚本口径）

| 指标 | 数值 | 含义 |
|------|------|------|
| 含 `<el-form>` 的 .vue 文件 | **29** | 全站表单载体清单（见第二节） |
| `<el-form>` 总数 | **58** | `^<el-form(?![-\w])` 安全匹配，已排除 `<el-form-item>` 误计 |
| 带 `:rules` 的表单 | **41**（71%） | **17 个表单完全没有 rules** |
| `<el-form-item>` 总数 | **372** | |
| 带 `prop` 的表单域 | **160**（43%） | **212 个表单域无法显示字段级错误**（连承载错误的能力都没有） |

### 一句话结论

**「有 rules 的表单」不等于「会被校验的表单」，而「没有 prop 的字段」是永久性的——它永远不可能出现字段级错误提示。**
本轮最严重的风险已不是「向导页缺 rules」（历史 P0「产品创建零校验」经核实**已修复**，见第三节 INFO-1），而是四类新形态：

1. **配置期声明的校验元数据在录入期被丢弃** —— 保全工作台（BLOCKER-1）：后端下发的 `required / validationType / validationPattern / validationMessage / allowClear` 五个字段在页面里**零引用**。
2. **无 rules 的整表单 + 顶层裸调用的加载函数** —— 系统配置页（BLOCKER-2）：加载失败静默保留默认值，点保存即全量 PUT 覆盖生产配置。
3. **手写 `if (...) return ElMessage.warning('请补齐 A 和 B')` 取代字段级规则** —— 费率表 / 定价包 / 佣金方案：一次说多个字段、错误不落字段、多条提示互相覆盖。
4. **同一业务概念多套值域与单位口径** —— 比例（0-1 vs 0-100）、材料清单（受控词表 vs 字典 vs 手打 tags）、条件规则编码（下拉 vs 自由文本）三处不一致。

### 已达标项（本轮确认为正向，非缺陷）

- **提交防重复与失败保留**：`saving / submitting / actionLoading / createSaving / rowsSaving` 等加载态普遍存在，且多处有显式注释说明「失败不关对话框、保留输入」（`views/product/rate-tables/index.vue:218-220`、`views/product/pricing-plans/index.vue` 等）。
- **提交前后反馈完整**：成功 toast + 列表刷新 + 失败交给拦截器（`src/api/http.ts:160-185` 已统一弹出后端业务原因），`showErrorIfUnhandled`（`src/api/http.ts:39-41`）已是标准工具。
- **日期区间天然有序**：全站 7 处区间选择器均为 `daterange` 控件，未发现「开始可晚于结束」的缺陷（详见 INFO-4）。
- **存在多个高质量校验范式**：产品创建向导的分步跳转（`views/product/create/index.vue:856-878`）、产品模板配置的页签跳转（`views/product/template-config/index.vue:623-703`）、规则引擎的 `whitespace: true`（`views/rule-engine/list/index.vue:235-245`）、条款列表的拒赔原因条件必填（`views/clause/list/index.vue:250-255`）——这些是改造时应复用的模板，而不是另起炉灶。

## 三、分级发现明细

### BLOCKER-1｜保全工作台「拟变更值」：配置期声明的 5 类校验元数据在录入期全部失效；受益人份额无合计校验

**现象**
保全办理页面最核心的录入区（「保全项与字段变更」表格的「拟变更值」列）是一个**裸 `el-input`**，全部字段一律纯文本框、无控件、无即时反馈、无必填标记；点击「保存字段草稿」时**不做任何校验**，空值会被当作「清空」提交。

**证据**
- `views/maintenance/workbench/index.vue:39-65` —— 该区域是原生 `el-table`（非 `el-form`），第 **47-48** 行是唯一的输入控件：
  `<el-input v-model="draftValues[changeKey(row)]" size="small" :disabled="isReadOnly" :placeholder="row.proposedValue || '请输入'" />`
- `views/maintenance/workbench/index.vue:291-323` —— 表行由配置规则生成，但**只读了 4 个字段**：`rule.visible && rule.editable`（:297-298）、`rule.expectedValueType`（:304 与 :315，仅作为 `dataType` 字段透传）。
- `views/maintenance/workbench/index.vue:464-478` —— `saveChanges()` 无任何校验，第 **471** 行 `canonicalValue: draftValues[changeKey(row)] || null`：**空字符串与"未填写"被折叠成同一个 `null`**。
- **grep 反证**：`validationType / validationPattern / validationMessage / allowClear / rule.required` 在 `views/maintenance/workbench/index.vue` 全文**零命中**（只有 `expectedValueType` 两处、`dataType` 五处）。
- 元数据定义（后端确实下发了这些字段）：
  - `src/api/maintenance.ts:271-281` —— `MaintenanceConfigurationFieldRule { fieldCode, required, visible, editable, allowClear, expectedValueType, validationType, validationPattern, validationMessage }`
  - `src/api/maintenance.ts:283-290` —— `MaintenanceFieldValidationType = NONE | EMAIL | MOBILE_CN | GENDER | ID_CARD_CN | POSTAL_CODE_CN | CUSTOM_REGEX`
- `views/maintenance/workbench/index.vue:288` —— 受益人份额取值 `beneficiary.shareRatio?.toString()`，全页**无 Σ=100% 校验**（`shareRatio` 全仓仅出现在 `api/policy.ts:37`、此处、`views/customer/detail/index.vue:126-127` 的只读展示）。

**影响**
1. 配置人员在「保全项配置」页辛苦配的 7 类校验（邮箱 / 手机 / 性别 / 身份证 / 邮编 / 自定义正则）在真正录入数据的页面上**完全不生效**——配置界面给出的能力承诺是假的。
2. `required` 为 true 的字段可以留空提交，且由于 `|| null`，必填与"清空该字段"在请求体里不可区分：该拒绝的和该清空的都变成 `null`。
3. 日期、金额、比例、证件号全部用自由文本框录入：错一位、少一位照样提交；受益人份额可以配成 3×50% 或合计 80%。
4. 这是资金与权益的直接入口（保额调整、退保、受益人变更），前端零护栏，一切依赖后端聚合拒绝 —— 与设计契约 `.impeccable.md` 的「输入即反馈」范式相反。

**改法**（按收益排序，全部为局部改动）
1. **把表行接进 `el-form`**：在表格外层加 `<el-form ref="fieldFormRef" :model="draftValues">`，为每行生成 `:prop="propPath(row)"`（如 `changeKey(row)`）与 rules，参考现成范式 `views/product/create/index.vue:336-338`（per-row `:prop` + rules）与 `:641-645`（`materialCodeRules($index)` 做行内重复检测）。校验失败时错误直接落在那一个单元格下方，用户不必猜。
2. **把配置元数据翻译成 rules**（新增一个纯函数即可，无架构变更）：
   - `required: true` → `{ required: true, message: validationMessage || \`请输入${fieldCode}\`, trigger: 'blur' }`
   - `validationType` → 内置正则表：`EMAIL`/`MOBILE_CN`(/^1[3-9]\d{9}$/)/`ID_CARD_CN`(18 位含 X)/`POSTAL_CODE_CN`(6 位)/`GENDER`(由下游控件保证)
   - `CUSTOM_REGEX` → `new RegExp(validationPattern)`，构造失败时降级为 only-required 并在控制台告警
3. **按 `expectedValueType` 换控件**：DATE → `el-date-picker`（`:value-format` 与提交口径一致）、AMOUNT → `el-input-number :precision="2"` 带货币单位、PERCENT → `el-input-number` 带 `%`，并在右侧显示格式化结果（金融字段「单位 + 结果预览」）。
4. **保存前置校验**：`saveChanges` 首行改 `if (!await fieldFormRef.value?.validate().catch(() => false)) return`（fail-closed 写法与 `views/product/create/index.vue:856-878` 一致）。
5. **受益人份额合计**：以 `objectId`（受益人）或 `itemCode` 分组，对 `policy.beneficiary.share` 行做组内合计校验，合计 ≠ 100% 时把错误挂到最后一行并给出行级提示「受益人份额合计需为 100%，当前 80%」。

### BLOCKER-2｜系统配置页：3 个表单零校验零 prop，加载失败时静默保留默认值，保存为全量 PUT

**现象**
系统配置页的三个 Tab（全局参数 / 邮件配置 / 短信配置）共 3 个表单、10 个表单域，**既无 `:rules` 也无 `prop`**；保存按钮在任何状态下都可点，保存函数不做校验；更严重的是配置**加载失败时页面不报错**，用户看到的是代码里的默认值，此时点保存会把默认值覆盖写入生产配置。

**证据**
- `views/system/config/index.vue:8`（`<el-form :model="form.globalConfig" …>`）、`:23`、`:41` —— 三个表单均无 `:rules`；10 个 `el-form-item` 全部无 `prop`。
- `views/system/config/index.vue:13`（`maxFileSize`）与 `:16`（`tokenExpiry`）—— **自由文本**输入，placeholder 是「如 10MB」「如 8h」，即"单位靠用户在字符串里自己写"。
- `views/system/config/index.vue:79-86` —— `loadConfigs()` 无 `try/catch`、无加载态、无失败态，且在模块作用域被裸调用（`loadConfigs()` :86，未 `await`、未 `.catch`）。
- `views/system/config/index.vue:73-77` —— 默认值兜底：`defaultPageSize: 20, port: 465, ssl: true`，`provider: ''`。
- `views/system/config/index.vue:88-96` —— `handleSave()` 无校验、无脏检查，直接 `await saveSystemConfigs(form)`。
- `src/api/systemConfig.ts:38-40` —— `/** 全量保存系统配置 */ export function saveSystemConfigs(data) { return http.put('/web/v1/system/configs', data) }` —— **全量 PUT**（注释自述）。
- `views/system/config/index.vue:56` —— 保存按钮只有 `v-permission` 与 `:loading="saving"`，**没有"加载成功"这一前置条件**。

**影响**
1. **数据事故路径**（最严重）：GET 失败（网络抖动 / 403 / 500）→ 页面无任何异常提示 → 表单显示默认值（SMTP 端口 465、SSL 开、provider 空）→ 管理员以为"当前配置就是空的"随手点保存 → **后端三节配置被默认值整体覆盖**，邮件与短信通道静默失效，且覆盖前无 diff 无二次确认。
2. 违反设计契约 `.impeccable.md:22`「已知字段用结构化控件」：文件上传上限、Token 过期时间本质是「数值 + 单位」，用自由文本承载导致 `10` / `10M` / `10MB` / `10240` 都能存，后端解析口径不可见。
3. SMTP 主机、邮箱账号、AccessKey 等字段无格式校验（写错只会在真正发信时才暴露）。

**改法**
1. **加载态与失败态**：`loadConfigs` 加 `try/catch`，维护 `loading` 与 `loadFailed`；失败时整页 `el-alert type="error"`「配置加载失败，请勿保存」并 `:disabled="!loaded"` 禁用保存按钮（`views/system/config/index.vue:56`）。这是 5 行以内的改动，但价值最高。
2. **只提交改动过的 section**：在 `form` 上加脏标记（`Object.assign` 回填时记录快照，提交时 diff 三个 section，只 PUT 变更部分）；若后端不支持部分更新，则在保存前 `ElMessageBox.confirm` 展示变更项 diff。
3. **结构化控件**：`maxFileSize` → `el-input-number`（`:min=1 :max=1024`）+ 单位 `el-select`（KB/MB/GB）；`tokenExpiry` → 数值 + 单位（分钟/小时/天）。提交时序列化成后端约定的单一字符串，保持兼容。
4. **补 rules + prop**：给每个域加 `prop` 与规则（host 域名格式、username 邮箱格式、accessKey 长度、signName 长度≤业务上限），trigger 用 `blur`（自由文本不宜 `change`，见 INFO-2）。
