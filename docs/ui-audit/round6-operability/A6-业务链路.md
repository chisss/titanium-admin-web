> **审计对象**：`titanium-admin-web/src`（前端）+ `titanium-admin`（BFF）+ 各业务域后端契约
> **审计日期**：2026-09-20
> **维度**：核心业务链路的**可达性 / 正确性 / 引导性**（非视觉一致性——视觉已五轮走查）

> **取证方法**：前端页面 ↔ 前端 API ↔ admin BFF ↔ 业务域 Controller ↔ 聚合根守卫，四层逐一对照，结论均附 `文件:行号`

## §0 一句话结论

**六条链路没有一条能完整走通**：链路 1/2/5 各断在 2 处以上，链路 3（核保决策）**整条不可达**，
链路 6（保全）是唯一接近达标的一条。根因高度集中为三类：

1. **前端状态门禁与后端状态机不一致**（`MANUAL_REVIEW` vs `REVIEW`、`status` vs `phase`）——「该能点的看不到」与「不该能点的能点」同时存在；
2. **后端有能力、BFF 未透传、前端无入口**（规则测试、核保风险评分、身故给付）——契约明列的流程步骤整段缺席；
3. **不可逆操作零门禁**（保单详情 11 个生命周期动作既无状态门禁、也无权限门禁）——与契约「Disable commands that are invalid for the current lifecycle state」正面冲突。

## §2 BLOCKER 详证

### B-1 🔴 核保决策链路整体不可达（链路 3 核心）

**结论：需人工裁决的核保案件打不开决策表单，案件在界面上无法推进。**

证据链：

1. 前端决策表单门禁 —— `src/views/underwriting/detail/index.vue:58`
   ```
   <template v-if="detail?.status === 'MANUAL_REVIEW'">
   ```
   列表页「审核」按钮同一门禁 —— `src/views/underwriting/list/index.vue:66`
   ```
   v-if="row.status === 'MANUAL_REVIEW'"
   ```
2. 后端**只有一条**路径产生 `MANUAL_REVIEW` —— `titanium-underwriting-domain/.../aggregate/Underwriting.java:328`（`handle(ManualReviewCommand)` 内 `newStatus = MANUAL_REVIEW`）。
3. 而 `ManualReviewCommand` **无任何 HTTP 入口**：全仓仅 `UnderwritingCommandService.manualReview` 一处引用（`titanium-underwriting-application/.../service/UnderwritingCommandService.java:83`），无 Controller 调用（`UnderwritingController.java` 端点清单：create/get/underwrite/inputs/decide/search/pending/statistics）；`UnderwritingApi`（Feign 契约）同样无该方法。
4. 实际「金额超阈值待人工」路径产出的是 **`REVIEW`** —— `Underwriting.java:178-179`
   ```java
   if (command.amount().amount().compareTo(AUTO_APPROVE_AMOUNT_LIMIT) > 0) {
       return UnderwritingEnum.UnderwritingStatus.REVIEW;
   ```
   阈值常量 `AUTO_APPROVE_AMOUNT_LIMIT = 100000`（`Underwriting.java:60`）。
5. `REVIEW` 在前端**没有任何处理分支**：详情页无决策表单、列表页无「审核」按钮 → **死胡同**。

> 附带核查（避免误判）：字典 `UNDERWRITING_STATUS` **已覆盖** `REVIEW`（`admin_business_dictionary_202608281445_dml.sql:262`），故状态**文案显示正常**，问题纯在动作门禁。

**改法**：把两处门禁从「等于 `MANUAL_REVIEW`」改为「状态非终态即可决策」，即 `['PENDING','MANUAL_REVIEW','REVIEW','AWAITING_INFO'].includes(row.status)`（判据直接对齐后端 `UnderwritingStatus.isTerminal()`，`UnderwritingEnum.java:63-68`）。**不要**在前端另抄一份终态清单，应从字典 extra 或后端补一个 `actionable` 标记下发，避免下次枚举演进再漂移。

### B-2 🔴 理赔「定损」无阶段门禁 —— 会做错、会被拒（链路 2）

**结论：用户在没做查勘的情况下可以填完整张定损单，提交后被后端拒绝，且能重复做已完成的查勘。**

1. 前端动作集**只按 status 计算，完全不看 phase** —— `src/views/claim/detail/index.vue:246-277`；`PROCESSING` 分支同时给出查勘与定损：
   `src/views/claim/detail/index.vue:255-262`
2. 后端定损守卫**要求当前阶段必须是 SURVEY** —— `titanium-claim-domain/.../aggregate/Claim.java:409-411`
   ```java
   if (this.phase != ClaimPhase.SURVEY) {
       throw new ClaimPhaseTransitionException(...)
   ```
3. 后端查勘守卫**不允许重复查勘** —— `Claim.java:427-432`（`target.getEnumCode() <= current.getEnumCode()` 即抛异常），故 phase 已是 SURVEY 时再点「查勘」同样被拒。
4. 阶段枚举与阶段推进事实 —— `ClaimPhase.java`：REPORT(1) → SURVEY(2) → LOSS_ASSESS(3) → APPROVAL(4)；立案后 phase 仍为 REPORT（`Claim.java:466`）。

**改法**：动作集改为 `(status, phase)` 二元判据：
- phase=REPORT → 只出「查勘」；
- phase=SURVEY → 只出「定损」；
- phase=LOSS_ASSESS → 只出「核赔通过」。
并在操作列上方用 `el-steps` 渲染当前阶段（`claimPhaseLabel` 已就绪，`claim/detail/index.vue:225`），把「当前在流程哪一步」显式化——这正是契约要求的引导。

### B-5 🔴 规则引擎「测试/校验」整段缺席（链路 5）

契约明列主流程为 `draft, edit, validate, test, publish, retire`。规则集页只有 草稿→追加规则→激活→停用，**无 validate、无 test**。

- 后端**四个**能力齐备 —— `titanium-rule-engine-web/.../controller/RuleEngineController.java`：
  `/execute/{ruleSetCode}`(:66) 试算、`/validate/{ruleSetCode}`(:82) 校验、`/score-card/{ruleSetCode}`(:98)、`/compute/{ruleSetCode}`(:118)
- admin BFF **一个都没透传** —— `RuleEngineProxyController.java` 仅 list(:30)、get(:37)、create(:44)、addRule(:51)、activate(:59)、deactivate(:66)
- 前端 API 相应无函数 —— `src/api/rule-engine.ts` 全部 6 个导出

**后果**：规则只能「激活后到出单环节才验证」，越过了契约要求的 validate/test 关口。激活属状态推进且影响出单定价，属高危盲发。

**改法**：BFF 补 `POST /web/v1/proxy/rules/{code}/validate`、`/execute` 两个透传（鉴权沿用 `RULE_ENGINE_TOGGLE` 或新增 `RULE_ENGINE_TEST`）；前端在规则集详情抽屉（`rule-engine/list/index.vue:74-99`）加「测试」按钮，弹 JSON 入参框 → 展示命中规则与结果。这与同仓 `views/maintenance/configuration/index.vue:164` 的「校验配置」`validate` 动作是同一范式，属**已有先例、照抄即可**。

### B-6 🔴 复效 / 失效：域层已实现，HTTP 面未暴露（链路 1）

- 域层完整：`ReinstatePolicyCommand.java`、`Policy.java:370-376`（守卫：仅 LAPSED，:372-373）、`PolicyReinstatedEvent.java`、回放处理器 `Policy.java:754`；失效侧 `LapsePolicyCommand` + `Policy.java:357`。
- **policy 域 web 层无端点**：`PolicyController.java` 生命周期端点清单（:277 至 :444）中只有 suspend/resume/terminate/cancel/waive-premium/dividend/annuity×2/mature/endorsement，**无 `/lapse`、无 `/reinstate`**。
- admin BFF `PolicyProxyController.java` 同样没有。
- 前端全仓 `grep -i reinstate|复效` **零命中**。

**改法**：policy-web 补 `PUT /{policyId}/reinstate`、`PUT /{policyId}/lapse` → BFF 补透传（建议码 `POLICY_REINSTATE`）→ 前端在「恢复保单」旁按 `status === 'LAPSED'` 出「复效」，按 `status === 'EFFECTIVE'` 出「失效」。

### B-7 🔴 理赔报案要求业务人员手输内部 UUID（链路 2 入口）

`src/views/claim/list/index.vue:83-88`：

```vue
<el-form-item label="保单ID" prop="policyId">
  <el-input v-model="createForm.policyId" placeholder="请输入生效保单ID（失焦自动带出客户）" ... />
```

客户 ID 同样手输（:86-88）。`autoFillCustomer`（:189-198）只是拿手输的 policyId 去 `getPolicyDetail` 反查客户——**前提仍是先知道内部 ID**。

### B-8 🔴 身故 / 全残给付不可达 —— 寿险理赔主链路缺失（链路 2）

- BFF **已就绪**：`ClaimProxyController.java:190` `/death-benefit`、`:203` `/disability-benefit`（均 `CLAIM_SETTLE`）
- 前端 API **已封装**：`src/api/claim.ts:149` `settleDeathBenefit`、`:154` `settleDisabilityBenefit`
- **视图零引用**（全仓 grep 仅命中 `api/claim.ts` 自身）
- 后端守卫明确要求按案件类型走专用通道 —— `Claim.java:268-282`（身故：须 APPROVED + `DEATH` 类型 + 材料齐备 + **受益人份额核算**）、`:301-315`（全残同理）

## §4 INFO 与「已核查为非缺陷」（避免后续误报）

### 4.1 有意为之的设计决策（勿再报为缺陷）

- **意向单不可新增/提交**：`src/api/insurance.ts:117-125` 有完整留痕说明——下游 `CreateProposalRequest` 无法承载参与方与标的，经此入口创建的意向单恒不可提交，故按 D-501-01 主动删除，页面保持只读，出单统一走 `POST /api/v1/issuances`。
- **规则集列表不做前台分页**：`rule-engine/list/index.vue:24-28,196-211` 已核实接口一次返回全量，传 `:total` 会造出假分页器。当前「不传 total」是正确处置。
- **保全旧 API 族（`/policies/maintenance/*`）6 个函数未被引用**：`api/maintenance.ts:433-484`。新族 `/maintenance/cases` 已完整覆盖（含审核），判定为**遗留死码**而非链路缺口。建议清理。
- **`views/maintenance/configuration`** 是契约 `draft→validate→submit→approve→publish→revision→retire` 的**样板实现**（`index.vue:163-169` 逐状态动作表 + 逐动作鉴权码 + 防自审 :173-174）。规则引擎与产品配置的缺口应以它为基准补齐。

### 4.2 经双侧核对后**推翻**的疑似缺陷（留痕）

| 疑似 | 推翻依据 |
|------|---------|
| `canCancel` 用 `PENDING/PENDING_EFFECTIVE`，与后端 `NOT_EFFECTIVE` 不符 | **误判**。读模型对写侧做了**有意映射**：`NOT_EFFECTIVE → PENDING_EFFECTIVE`，见 `PolicyProjectionEventHandler.java:284,292` 与 `PolicyViewRepository.java:89,97`（后者明文写「读模型状态 PENDING_EFFECTIVE 是写侧 NOT_EFFECTIVE 的有意映射」）。前端面向读模型，`canCancel`（`policy/detail/index.vue:297-299`）**正确**。其中 `'PENDING'` 分支为死码，无害。 |

| 核保详情页「取消」按钮丢上下文 | 轻微。`:75` `$router.back()`，且 `TiDetailHeader` 已具备 `hasHistory()` 探测（`components/TiDetailHeader/index.vue:66-71`）。归入 W-1。 |
