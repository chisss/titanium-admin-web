## 一、结论摘要

**一句话**：接口级权限是本轮唯一达标的一层（262/264，且有运行时 fail-closed 兜底），**菜单级权限形同虚设、按钮级权限只覆盖 1/3、字段级权限全站为零**；并且在"权限"这一维度上存在 **1 条真实的自我提权路径**与 **1 条脱敏配置回写擦除链**。

## 二、菜单权限

### 2.1 菜单树来源链路（这一段是对的）

```
ApiResponse<MenuNode[]> ← GET /web/v1/menus/user-tree
  MenuController.java:81-90        @PreAuthorize("isAuthenticated()")
  MenuApplicationService.java:111-145  getUserMenuTreeByUserId(userId)
      → roleIds → permissionRepository.findPermCodesByRoleIds(roleIds)
      → menuRepository.findByPermCodes(permCodes)  → 补父节点
  MenuRepositoryImpl.java:49-56    findByPermCodes = 精确 contains(permCode)
```
- 前端 `stores/menu.ts` → `api/menu.ts` 调该接口，`Sidebar.vue:33-65` 直接渲染 `menuTree`，**不做本地过滤**（正确：单一事实源在后端）。
- `MenuApplicationService.java:111-145`：`roleIds` 为空 → 空树（fail-closed，正确）。
- ✅ **结论**：侧栏不会出现用户无权点的菜单。

### 2.2 ⛔ B1 —— 路由级权限层完全不存在（"菜单是唯一闸门，而闸门可绕过"）

**取证**：
- `router/index.ts:15` —— `routes: [...staticRoutes, ...dynamicRoutes]`：**全部业务路由在应用启动时一次性注册**。
- `router/index.ts:20-56` —— `beforeEach` 只做三件事：查 token / 白名单（`:28` `['/login','/404']`）/ `loadUserInfo()`。**全分支没有读取 `to.meta.permission`**。
- 全仓 `grep -rn "addRoute"` → **0 命中**（无动态注入）。
- `router/dynamicRoutes.ts` 中 26 处 `meta.permission` 声明（如 `:27 product:list`、`:33 product:create`（hidden）、`:89 policy:detail`、`:199 maintenance:view`、`:231 claim:config`、`:371 system:dict`）**全部是死元数据**。
- `router/staticRoutes.ts` 无 `/403` 路由；`api/http.ts:159,177` 对 403 只弹 `ElMessage.error('无权限访问该资源')`。

**真实危害（不夸大）**：后端 262/264 端点有 `@PreAuthorize`，所以深链无权页面**拿不到业务数据**——危害是另外三条：
1. **契约未落地**：`.impeccable.md:30` 明确要求 route permission 与按钮权限同源对齐，当前 26 处声明一处未生效。
2. **8 个 `isAuthenticated()` 端点可被"菜单外"访问**：`DictController.java:56`（字典类型）、`:112`（字典数据）、`MenuController.java:81`（本人菜单树）、用户信息/部门下拉 —— 这些刻意豁免业务码（`AdminPermission.java:16-18` 已声明理由），但意味着**无权访问"系统管理 > 字典管理"菜单的账号，仍可直连 `/web/v1/dicts/types` 读全量字典**。
3. **空壳页面 + 误导**：无权用户直达 `/system/role` 会看到完整表格骨架、筛选器、按钮（按钮还可能因 `v-permission` 被摘掉），随后每列一行红色 toast，用户无从判断是"没数据"还是"没权限"。

**改法（三步，按序）**：
1. 给 `beforeEach` 加第三段判定（在 `loadUserInfo()` 之后）：
   ```ts
   // router/index.ts，紧接 userStore.loaded 分支之后
   const required = to.meta?.permission as string | undefined
   if (required && !userStore.hasPermission(required)) return next('/403')
   ```
2. **新增 `views/403/index.vue`** 并在 `staticRoutes.ts` 注册；`api/http.ts:177` 的 403 分支改为 `router.replace('/403')`（保留 toast 作为补充）。
3. 🔴 **不要直接照抄 `meta.permission`** —— 见 W3：7 个码全站无人持有，直接启用会让**所有详情页对所有人（含超管）不可达**。必须与 W3 合并执行。

### 2.3 ⛔ B4 —— `claim:config` 菜单：打开即全 403

**取证**：
- `ClaimConfigProxyController.java:42-76` —— 理赔配置的 **GET 端点也要求 `claim:config:edit`**（如 `:42`、`:52`、`:62`）。
- 种子把 `claim:config` 作为**菜单** perm_code（列于"种子有但后端从不引用"集合，见 §3.4）。
- 前端 `views/claim/config/**` 全目录 `v-permission`/`hasPermission` 命中数 = **0**（`grep -rn "v-permission\|hasPermission" views/claim/config/ | wc -l` → 0）。
- 该页唯一入口是菜单，因此任何**被授予 `claim:config` 菜单但未同时持 `claim:config:edit`** 的角色，进入后全部请求 403，页面彻底不可用，且没有任何前端提示说明缺哪个码。

**改法**：菜单读写码拆开 —— 新增 `claim:config:view` 用于 GET（`ClaimConfigProxyController` 的读端点改用它），写端点保留 `claim:config:edit`；并把 `t_menu` 中理赔配置菜单的 perm_code 改用 `claim:config:view`。

### 2.4 ⚠️ W4 —— 菜单码 ↔ 接口码错配（另三处）

| 菜单 perm_code | 页面实际调用的接口要求的码 | 后果 |
|---|---|---|
| `policy:application`（投保单查询） | `policy:list`（`InsuranceProxyController.java:77-78` `/proposals`） | 双向错配：只授 `policy:application` → 菜单可见、请求全 403；只授 `policy:list` → 数据可查、菜单不可见 |
| `policy:intention`（意向单查询） | `policy:list`（同上） | 同上 |
| `system:dict`（字典管理） | 读 = `isAuthenticated()`（`DictController.java:56,112`） | **码形同虚设**：无该码也能直连读全量字典；写端点（`:76/:87/:101`）用 `system:dict:create/edit/delete`，与菜单码无关 |

**改法**：投保单/意向单菜单改用 `policy:list`；字典管理读端点补 `@PreAuthorize("hasAuthority('system:dict')")`，或在 `AdminPermission` 注释中显式登记该码为"菜单专用、无端点消费者"。

### 2.5 ⚠️ W3 —— 7 个 `*:detail` 路由码"全站无人持有"（补守卫时的地雷）

`router/dynamicRoutes.ts` 为详情页写了 **7 个种子与后端都不存在的权限码**：

| 行 | 码 | 种子有？ | 后端 `AdminPermission` 有？ |
|---|---|---|---|
| `:39` | `product:detail` | ✗ | ✗ |
| `:89` | `policy:detail` | ✗ | ✗ |
| `:127` | `clause:detail` | ✗ | ✗ |
| `:159` | `billing:detail` | ✗ | ✗ |
| `:225` | `claim:detail` | ✗ | ✗ |

（另 `directives/permission.ts:8` 的文档示例 `policy:maintenance:apply` 同样全站不存在。）

**危害**：一旦按 §2.2 落地路由守卫，这 7 个详情页将对**所有普通业务角色**不可达，而详情页恰是承接列表"详情"按钮的必经路径 → **上线即白屏**。（`SUPER_ADMIN` 因前端 `permissions` 含 `*` 而豁免，`stores/user.ts:110-112`。）

**改法（二选一，推荐前者）**：
1. 详情页 `meta.permission` 一律**继承其列表页的查看码**（`policy:detail` → `policy:list`、`product:detail` → `product:list`…），语义正确且零种子改动；
2. 或把这 7 个码补进 `t_permission` 与 `AdminPermission`，并绑到对应角色 —— 成本高且要重跑一次全量角色数据修复。

### 2.6 ⚠️ W5 —— `SUPER_ADMIN` 通配符两处不对称 + 权限变更需重登

- `/user-info` 侧：`UserInfoApplicationService.java:64-71` —— `roleCodes.contains("SUPER_ADMIN")` → 返回 `List.of("*")`（`AdminConstant.java:19,22`）。
- 安全上下文侧：`AdminUserDetailsService.java:64-76` —— authorities = **DB 精确码 + `ROLE_*`，不含 `*`**。
- 菜单侧：`MenuApplicationService.java:111-145` —— **完全不认 `*`**，只按 `findPermCodesByRoleIds` 精确匹配。
- 前端：`stores/user.ts:110-112` —— `hasPermission = permissions.includes(perm) || permissions.includes('*')`。

**后果（三条，均为潜伏态）**：
1. 若新增权限码但漏绑 role 1（`t_role.id='1'`, `role_code='SUPER_ADMIN'`，见 `admin_init_202507191000_seed_dml.sql:16-17`），则**前端显示按钮、后端 403** —— 超级管理员沦为"按钮点不动"，日志里只有一条 `AccessDeniedException`。历史已发生过同类事故（见 §3.4 注释墓碑）。
2. 超管的菜单来自 role 1 的菜单绑定，与 `*` 无关 —— 解绑一个菜单即对超管生效，但所有按钮仍在（两套判定不同源）。
3. `permissions` 是**会话内存态**（`stores/user.ts:76-83`，`loaded` 标志一次性加载）：管理员改了角色的权限后，**在线用户的前端在重新登录前一直显示旧权限**（后端因 `JwtAuthenticationFilter.java:59-64` 每请求重查 DB 而即刻生效）。

**改法**：把 `*` 语义下沉到安全层（`AdminUserDetailsService` 对 SUPER_ADMIN 注入 `*` authority + 自定义 `AuthorizationManager` 解释它），使三处同源；前端提供"刷新权限"入口（把 `loaded` 置回 false 重拉）。

### 4.1 ⛔ B5 —— 自我提权：`system:user:assign-role` 可自挂 `SUPER_ADMIN`（真越权）

**取证链**：
1. `AdminUserController.java:165-170` —— `PUT /web/v1/users/{id}/roles` 只要求 `system:user:assign-role`，`id` 是路径参数，**可以是自己**，请求体是任意角色 id 列表。
2. `admin_init_202507191000_seed_dml.sql:16-17` —— `t_role` 中 `id='1'` 即 `role_code='SUPER_ADMIN'`、`role_name='超级管理员'`、描述"拥有全部权限"。
3. `AdminUserDetailsService.java:64-76` + `AdminUserDetails.java:52-62` —— authorities 每请求从 DB 重查（`JwtAuthenticationFilter.java:59-64`），故**下一个请求即刻生效**，无需重新登录。
4. `UserInfoApplicationService.java:64-71` —— 拿到该角色后 `/user-info` 返回 `['*']`，前端 `stores/user.ts:110-112` 全量放行。
5. **全仓 `grep -rn "SUPER_ADMIN"` 仅 1 处命中**（`UserInfoApplicationService.java:65`）——即：没有"不能给自己分配角色"的校验、没有"`SUPER_ADMIN` 不可被分配/编辑/删除"的保护。

**危害**：任何持有 `system:user:assign-role` 的运营账号（一个本意只是"给新人挂个角色"的码）可在 2 个请求内获得全部 103 个权限码 + 前端全量放行。教科书式的横向→纵向提权，**当前无任何一层阻止**。

**改法（三条同时上）**：
1. `AdminUserApplicationService.assignRoles` 前置校验：禁止 `targetUserId == currentUserId`（需从 `UserPrincipal` 传入 currentUserId）；
2. 禁止把 `role_code = 'SUPER_ADMIN'` 的角色分配给任何用户（初始化脚本除外）；
3. `SUPER_ADMIN` 角色本身不可编辑/不可删除（`RoleController.java:93` update、`:113` assign-permissions 对 role 1 一律 403），并在 `AdminConstant` 旁写明理由。

## 五、字段级权限 —— 结论：**前端 0 实现，后端仅 1 处且是租户级（非角色级），并已衍生一条数据损坏链**

### 5.1 ⛔ B2 —— 字段级权限全站为零 + 脱敏配置回写擦除链

用户明确要求的场景（"精算只能改费率，运营不能修改核保规则"）在当前代码里**没有任何对应机制**。已有的最接近实现只有一条链路，且是有缺陷的：

```
admin 前端编辑器  ──PUT──▶  admin BFF  ──Feign(带 X-Authorities)──▶  maintenance 下游
MaintenanceConfigurationEditor.vue:194                   MaintenanceServiceClient.java:110-150
        emit('save', cloneRaw(form))                     MaintenanceConfigurationWebMapper.java:75-80
                                                           (toFieldRule 入站**不做**任何脱敏/回填)
```

**擦除链的每一步（均已实读取证）**：

| # | 位置 | 行为 |
|---|---|---|
| 1 | `MaintenanceCaseProxyController.java:102-143` + `MaintenanceServiceClient.java:110-150` | admin 调下游时转发 `X-Operator-Id` + `X-Authorities`（**全仓唯一会转发 authorities 的 Controller**） |
| 2 | `MaintenanceConfigurationRequestContextResolver.java:26,77`（下游） | `SENSITIVE_VIEW_PERMISSION = "maintenance:sensitive:view"`，据此计算 `sensitiveDetailsVisible` |
| 3 | `MaintenanceConfigurationWebMapper.java:92-95,202-209`（下游） | 不可见时把 `conditionRuleCode` / `expectedValueType` / `validationType` / `validationPattern` / `validationMessage` **置 `null`** 出站 |
| 4 | `MaintenanceConfigurationMirror.java:25,38`（admin） | `sensitiveDetailsVisible` **接到了**，但全仓 grep：**零消费者**（未映射到任何 VO、未暴露给前端） |
| 5 | `MaintenanceConfigurationEditor.vue:28,36,50,61-62` | 前端把 `expectedValueType`/`validationMessage`/`conditionRuleCode` 直接 `v-model` 绑到输入控件；`:157-167` watch 克隆源定义时只补 `validationType \|\| 'NONE'`，**对 `null` 无任何处理** |

### 5.2 ⛔ B3 —— 保全项级操作/查看权限码：三处声明，零处执行

`MaintenanceConfigurationEditor.vue:61-62` 提供"操作权限 / 查看权限"两个多选（`controls.accessRule.operationPermissionCodes` / `viewPermissionCodes`，默认 `['maintenance:item:operate']` / `['maintenance:item:view']`）。全仓追踪这一对码：

| 出现位置（下游 `titanium-maintenance`） | 用途 |
|---|---|
| `MaintenanceConfigurationWebMapper.java:163-170` | DTO → 领域对象（入站映射） |
| `MaintenanceConfigurationWebMapper.java:239-241` | 领域对象 → VO（出站映射） |
| `MaintenanceConfigurationValidator.java:159,176-177` | 合并两集合校验"敏感字段是否声明了 `maintenance:sensitive:view`" |
| `MaintenanceItemConfigurationHasher.java:118,134` | 计入内容哈希（配置一致性） |
| **运行时鉴权** | **不存在**：全仓无任何一处把"当前操作人的 authorities"与 `operationPermissionCodes`/`viewPermissionCodes` 做比对 |

**后果**：管理员界面上填的"操作权限 / 查看权限"**从不生效**——任何能进入某保全项工作台的人都能操作它。这是"虚假安全感"型越权：配置者以为已经限定了办理人，实际没有。（已确认 `MaintenanceCaseQueryAccessResolver.java:12-14` 与 `MaintenanceCaseFieldMasker` 用的是全局码 `maintenance:sensitive:view`，而非 per-item 的 accessRule。）

**改法**：在下游 `MaintenanceCase` 的命令入口（立案/提交/审批）与查询入口各加一个 `MaintenanceAccessRuleGuard`，把 `definition.controls().accessRule().operationPermissionCodes()` 与请求上下文的 authorities（admin 已通过 `X-Authorities` 转发）求交，为空即 `AccessDeniedException`。**转发通道已经建好（`MaintenanceCaseProxyController` 的 `authorities()` helper），只差下游一个消费点。**

### 5.3 其余既有机制：只有"租户级脱敏"，没有"角色级字段权限"

- `ActuarialDataAccessService.java`（admin）—— `ActuarialMaskingPolicy.maskInternalAmount/maskInternalFields`、`maskPremiumCalculation`/`maskCommissionData`、`INTERNAL_COST` 渠道掩码、`"***"` 替换 `componentCode`/`nodeCode`。**按租户/通道做，不是按角色**。
- `ActuarialDataAccessController.java:37-62` —— GET 用 `product:actuarial`、PUT 用 `product:actuarial:edit`。粒度是"整个资源"，不是字段。
- 其余 20+ 个业务页面：**没有任何字段级读写控制**。

### 5.4 字段级权限的落地结论与推荐路径

**结论**：全站字段级权限 = **0**。唯一可复用的成熟先例是下游 maintenance 的 `sensitiveDetailsVisible` + `maintenance:sensitive:view`（角色级字段掩码），但它在 admin 侧的最后一个环节（镜像 → VO → 前端）**断了**。

**推荐落地路径（三步可独立交付）**：

1. **先修数据损坏（止血，约 1 天）**——不改架构，只堵擦除链：
   - admin：`MaintenanceConfigurationMirror` → VO 增加 `sensitiveDetailsVisible` 透传（`MaintenanceConfigurationMirror.java:38` 的值已就位）；`MaintenanceConfigurationEditor.vue:26-42` 受影响列改 `:disabled="!sensitiveDetailsVisible"` + 表头提示"（无查看权限，仅展示脱敏值）"；`submit()` 在 `!sensitiveDetailsVisible` 时不回写这些字段（或整体禁用保存并提示）。
   - 下游：`MaintenanceConfigurationWebMapper.java:75-80` 的 `toFieldRule` 增加入站防呆——`sensitiveDetailsVisible == false` 且入参含 `null` 敏感字段时，以库中现值回填（或直接 400）。
2. **再定机制（约 1 周）**——引入**统一字段权限模型**，避免第二套方言：
   - 前端：加 `v-field-permission="'policy:premium:rate'"` 指令（语义 = 无码则控件 `disabled` 且**保留可见**，与 `v-permission` 的"移除 DOM"明确区分），并接到表单 schema，使字段级权限声明与 `el-form-item` 同源；
   - 后端：`@PreAuthorize` 之外增加**字段级校验**（写端点接收 DTO 后按 authority 剥离/拒绝无权字段），否则前端 `disabled` 只是"礼貌"——本项目已实测证明按钮层不设防时后端仍拦得住，字段层必须同样有后端呼应；
   - 数据来源沿用 `t_permission`（`perm_type` 增加 `FIELD`），使 `GET /web/v1/menus/permissions/tree` 可扩展到字段粒度，角色配置界面无需新造轮子。
3. **用户点名的两个场景直接落码**：`product:rate-table:edit`（精算改费率——已有码，只需补前端守卫）与核保规则（`underwriting:decide` / 规则集 `rule-engine:edit`——已有码，需补**字段级**"只读"语义，即无码时规则字段 `disabled` 而非隐藏整页）。

### 8.1 ⚠️ W6 —— 只隐藏，不禁用；且无响应式

- `directives/permission.ts` 仅在 `mounted` 钩子判定并 `removeChild`：**权限变化后不会恢复/更新**（会话内权限为内存态，见 W5-3）。
- 语义问题：禁用态能告诉用户"这个动作存在但你无权"，隐藏则让用户完全不知道该功能——对管理员排障尤其不利。当前两套语义并存：系统管理页用指令（隐藏），`maintenance/configuration/index.vue:178-184` 用 `hasPermission` 过滤 `actionsFor()`（等价隐藏），产品列表下拉项用 `hasPermission`（`product/list/index.vue:148-167`）。
- 已有正面样板：`maintenance/configuration/index.vue:178-184` 注释明确解释了"前端先过滤，而不是把按钮全部渲染出来等后端 403"的取舍。

### 8.2 ⚠️ W7 —— 403 无承载页

`api/http.ts:177` 的 403 分支只弹 toast；用户点进无权限菜单后停在半渲染页面，靠 toast 自我解释。**改法**：新增 `views/403/index.vue`（提供"返回首页 / 申请权限"两条出口），403 分支改为路由跳转（toast 可保留）。
