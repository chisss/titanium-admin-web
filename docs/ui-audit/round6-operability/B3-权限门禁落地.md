> 批次日期：2026-09-20
> 上游审计：同目录 [A5-权限.md](./A5-权限.md)（三级权限覆盖率审计，只读取证）
> 设计契约：`/Users/sunwei/titanium-project/.impeccable.md` 第 30 行 —— "Keep button permissions aligned with backend authorities and route permissions."
> 判定总纲：**前端比后端更严 = 拦住后端本可接受的输入；比后端更松 = 放行一次必然失败的提交。两者都是缺陷。**

## 一、本轮判据（与 A5 的差别）

A5 是**覆盖率审计**，判的是「有多少按钮受控」。本轮是**接线正确性落地**，判的是
「受控按钮接的那个码，是否就是它落到的那个端点要求的码」。

差别在**粒度**：覆盖率把「理赔详情 8 个动作」记作 1 条待办，接线正确性要求逐动作对齐
`POST /{id}/survey → claim:survey` vs `PUT /{id}/status → claim:approve`——**8 个动作分属 3 个不同的码**，
统一用一个码收放，无论取交集还是并集都会造出「点了必然 403」或「该看的人看不到」。
故本轮的交付物不是「补了 N 个 `v-if`」，而是**「每个写入口 ↔ 它的端点码」的逐条对齐 + 机械守卫**。

### 2.2 三处「一页两码」的判据（本轮最容易做错的地方）

1. **模式分叉**（`clause/edit`、`product/create`）：一页同时服务新建与编辑，但后端是**两个端点两个码**。
   按模式取码，**不取并集**——只给「新增条款」的运营不该能改已生效条款。
2. **必经 + 旁路分叉**（`product/template-config`）：一次保存分叉到 `PUT /templates/{id}`（`product:edit`，
   必经）与 `POST /{id}/life-config`（`product:config`，寿险页签）。两码各管各的：取并集会让只有
   `product:edit` 的人看到改不了的页签，取交集会让只有 `product:config` 的精算连模板都存不了。
3. **整块 vs 单按钮**（`underwriting/detail`、`claim/config`）：决策表单是整块写入口，无权限时
   **连区块都不该出现**；操作列同理——留一个空「操作」表头，用户会以为页面坏了。

### 2.3 机械守卫：`ui-guard` 规则 I-02

新增规则 **I-02「可达写接口的视图必须有权限门（不得靠后端 403 兜底）」**，
与 I-01 共用同一套闭包机器（`apiWriteFns` + 引用级 `isWrite` 递归）——
🔴 **故意的**：两条规则对「什么是写动作」必须同口径，否则会出现「I-01 认为在写、I-02 认不出来」的缝。

- 基线实测：**27 个视图可达写接口，其中 1 个整文件零权限门**（`policy/detail`，即本轮第 9 个文件）。
- 判据刻意取**文件级**而非元素级：本轮 8 个零门页的共同特征就是「整文件一处门都没有」；
  而元素级在本仓有**三种合法形状**（`v-permission` / 带 `hasPermission()` 的 `v-if` / 动作清单按权限过滤），
  第三种在正则里无法与「恰好遍历一个列表」区分，硬判会大量误报。
- **一条被假阳性淹没的守卫会立刻失去信任（I-01 的教训）**，故取窄而准；「五个按钮漏了一个」
  由 `tests/permission-gate-contracts.test.mjs` 按端点逐个钉死。

## 四、本轮新增的三类发现（**可配置但无执行器**）

三者同源：**界面/数据层登记了某能力，执行层无人读取**。前两者已在本轮**披露或锁死**，
第三者的修法取决于产品定义（是补执行点还是撤登记），列为 open。

### F1 — 保全项「操作权限 / 查看权限」：三处声明，零处执行（= A5 的 B3）**已披露**

后端对 `accessRule` 的生产读取只有 3 类，**均非鉴权**：①
`MaintenanceConfigurationValidator:159/176-177`（校验引用的码在注册表中存在）；②
`MaintenanceItemConfigurationHasher:118`（计入版本哈希）；③ `MaintenanceConfigurationWebMapper:163/240-241`（DTO 映射）。
案件受理/审核/执行/查询**均不读取**。真正生效的敏感字段查看权限走服务端硬编码常量
（`MaintenanceCaseQueryAccessResolver` 的 `maintenance:sensitive:view`），与此处配的值无关。

⇒ 处置：`MaintenanceConfigurationEditor.vue` 增加 `el-alert`（warning）如实披露。
**不写这句，运营会以为「配了就只有指定角色能操作」——合规口径下的静默失效，比缺功能更危险。**
执行器另行立项，此处只做如实披露。

### F2 — 路由 `meta.permission` 是**死元数据**，其中 7 个码后端不存在 **已锁死**

实测 `src/` 全仓**无任何**地方读取 `meta.permission`：`router/index.ts` 直接
`routes: [...staticRoutes, ...dynamicRoutes]` 全量注册。菜单可见性的权威在**后端**——
`MenuController /user-tree` → `MenuApplicationService.getUserMenuTree` →
`menuRepository.findByPermCodes(角色持有的码)`。

由此得到两个结论：

1. **菜单权限是真的**：`t_menu` 103 个码（30 菜单/目录 + 73 按钮）与 `t_permission` 128 个码
   **双向零 orphan**；`AdminPermission` 103 个常量**无一缺失权限行** ⇒ 每个 `@PreAuthorize` 的码都可被授予。
   （A5 §2.1 结论一致，本轮独立复算。）
2. **`meta.permission` 写错不影响行为，但也不提供保护**。其中 12 个码不可授予，7 个**两端都不存在**：
   `policy:detail` / `product:detail` / `clause:detail` / `claim:detail` / `customer:detail` /
   `billing:detail` / `underwriting:detail`。**这不是当前的缺陷，是补守卫时的地雷**——
   一旦有人把 `meta.permission` 接进路由过滤（A5 的 B1 想做这件事），这 7 个页面会**对所有人永久不可见**。
   ⇒ 用例 ⑩ 同时钉死「无消费点」与「这 7 个码」：接了就先红，逼先修码。

### F3 — 权限树中 20 个可勾选码无任何执行器 **已冻结存量**

`t_menu`（按钮型 `'F'`）与 `t_permission` 共同构成角色配置界面的权限树，勾选即授予。但一个码要被
**真正执行**须落到三处之一：① 端点鉴权（`@PreAuthorize`，或 `contextResolver.require(request, SUBMIT)`
这类本地常量）；② 菜单可见性（C/M 型 `perm_code`）；③ 前端门。**三者皆无 = 勾了完全没反应**。

实测 20 条（含 `customer:create/edit/delete`——`CustomerProxyController` 只有 3 个 GET，全仓 Java 对这 3 码
**引用 0 处**；以及 7 个 `*:view`、7 个 `*:export`）：

```
billing:export  billing:view  claim:export  claim:view  clause:view
customer:create  customer:delete  customer:edit  customer:export  customer:view
maintenance:export  maintenance:view  policy:export  policy:view
product:export  product:view  system:dict:refresh  system:role:delete
underwriting:export  underwriting:view
```

> 🔴 候选原有 25 条，经复核 **5 条确已执行**：`maintenance:config:submit/approve/publish/retire`
> 走 `MaintenanceConfigurationController` 的 `contextResolver.require(request, SUBMIT)`；
> `maintenance:sensitive:view` 走 `AccessResolver` 硬编码常量。
> **判定方向刻意保守**：只要码出现在任何「含权限判定标记」的 Java 文件里就算已执行——
> 漏判可接受，误判（把活码说成死码）会立刻摧毁用例可信度。

⇒ 用例 ⑪ 冻结存量：新增一个空权限即 RED，逼补齐执行点或说明为何先登记。

## 七、未闭环项（登记，供下一批）

### B4 · 理赔配置中心：菜单码与端点码的**两级设计**存在死胡同

- 菜单 `62` 的 `perm_code = 'claim:config'`（页面级）；而其全部 ~30 个端点（**含 GET**）
  要求 `claim:config:edit`（按钮级，`id=442`）。
- ⇒ 只授 `claim:config`：菜单可见 → 打开后**每个面板的列表请求都是 403**；
  只授 `claim:config:edit`：`findByPermCodes` 精确匹配 ⇒ **菜单根本不出现**。
  **两条路都进不去一个能用的页面。**
- 两种修法（择一，需产品定义）：
  1. 菜单 `perm_code` 改为 `claim:config:edit`（一码到底，最简；语义上「看不到读不了的页」也成立）；
  2. 后端 GET 改用 `claim:config`、写保留 `claim:config:edit`（两级语义最正，但要动 ~30 个端点的注解）。
- **本轮不动的理由**：① 改种子须**新增 changeset**（既有 changeset 不可变，`runOnChange:true` 亦然，
  改存量会破坏已部署库的校验和）；② 两种修法分属「数据」与「后端契约」，取舍取决于「页面级权限是否要独立存在」，
  非测试期可自行判定。

## 八、风险与后续

- **最大风险是「以为已受保护」**：F1/F3 的共同形态是界面登记了能力而执行层无人读取。
  本轮对 F1 做了页面级披露、对 F3 做了冻结，但**披露不等于防护**——清单本身要有人消费。
- **⑪ 的保守偏差**：判定「已执行」的口径很宽（码出现在任何含权限判定标记的 Java 文件里即算）。
  因此真实空权限数**可能多于 20**，不会是更少。要收窄口径，需按「码是否真的参与某次判定」逐点解析注解与
  方法调用，而非按文件。
- **⑨ 依赖库种子**：种子是 dev 环境的语料，生产库若另有权限行，⑨ 的判据面会随之变化。
