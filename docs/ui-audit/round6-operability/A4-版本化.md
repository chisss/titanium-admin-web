# A4 — 版本化能力全链路审计（前端可见性 + 后端支撑）

**审计日期**: 2026-09-20
**审计维度**: 版本化全链路能力现状（领域模型 → 接口暴露 → BFF 代理 → 前端可见性）
**审计方式**: 纯实读代码取证（前端 + 后端 + BFF 三层），未运行任何服务、未修改任何源码
**设计契约**: `/Users/sunwei/titanium-project/.impeccable.md`（第 21 行「Never hide tenant, product, version, status, or effective-time context」；第 18 行「draft, edit, validate, test, publish, retire」）
**硬性业务要求**: 产品、规则、费率全部版本化，可**对比差异**、可**回滚**，满足监管审计

---

## 一、结论摘要

版本化的**"版本号 + 状态机"这一层是建成的**（产品/条款/费率表/定价包四类实体都有版本字段与 DRAFT→PUBLISHED→RETIRED 类状态机），
但硬性要求中的**"对比差异、回滚、监管审计"三项能力在前后端全链路 0 命中**（详见 §三 B1/B2/B3）。
即：**能发新版本，但既看不出两版差在哪，也退不回去，且管理台查不到是谁在什么时候改了哪一版。**

另发现两类结构性问题：
1. **动作存在但通道断开**——条款修订后端有端点、BFF 未代理、前端无入口（三段断裂，W2）；规则集根本无修订命令（W3）。
2. **生效期在 UI 上不可管理**——产品的销售起止在新建/修订页无任何输入（W1）；费率表/定价包的失效时间前端无输入（W7）；费率表发布不做跨版本有效期重叠校验（B4）。

## 四、分项详述

### 4.1 产品版本化（建成度最高，缺口在"谱系可见性"与"生效期"）

**版本产生机制完整**：`InsuranceProduct` 是事件溯源聚合，修订不走原地更新，而是
`AggregateLifecycle.createNew(InsuranceProduct.class, () -> new InsuranceProduct(revisedEvent))` 为 `newProductId` 建立**独立事件流**
（`InsuranceProduct.java:297-309`），新版本落 DRAFT 并经 `originalProductId` 溯源（`on(ProductRevisedEvent)`, `:427-455`）。
BFF 侧明确注释「产品是版本化实体，变更一律走本修订端点生成新版本，不存在原地更新语义」（`ProductProxyController.java:170-173`，D-501-08）。**这是五类实体中设计最正确的一处。**

**缺口 A — 版本谱系不可见**：`originalProductId` 已贯通 `InsuranceProduct:96` → `ProductView:90` → `ProductQueryResult:47` → `ProductResponse:37` → BFF `ProductMirror:56`，但前端 `grep originalProductId` **0 命中**。数据在手上，只是没画。

**缺口 B — 生效期断裂（W1）**：`CreateProductDTO.java:50,52` 有 `saleStartTime/saleEndTime`，但 `views/product/create/index.vue` 与 `revise/index.vue` 中 grep `sale` / `销售` **均 0 命中**。
更严重的是修订路径：`ProductRevisedEvent.java:23-33` **未携带任何销售期字段**，`on(ProductRevisedEvent)`（`:427-455`）也未恢复 `saleStartTime/saleEndTime`
⇒ **修订出的新版本销售窗口为 `null`**。而产品详情页却在展示"销售起期/销售止期"（`detail/index.vue:45-46`）——该两行在现有流程下恒显示 `-`。

### 4.2 条款版本化（后端有、BFF 无、前端无 — W2）

后端完整：`Version` 值对象含 `nextVersion()` 递增（`valueobject/Version.java`），`handle(ReviseClauseCommand)` 仅允许 ACTIVE 修订、生成 `newClauseId` 独立事件流（`Clause.java:295-310`），web 端点 `POST /web/v1/clauses/{clauseId}/revise`（`ClauseController.java:180`）。

**断点在第 2 段**：admin BFF `ClauseProxyController.java` 的 13 个 mapping 中**没有 `/revise`**（仅 list/detail/create/update/submit-approval/approve/reject/activate/inactivate/delete/coverages）。
**第 3 段**：`api/clause.ts` 的 12 个导出函数中无 revise。
⇒ 前端即使补了入口也会 404。**BFF 是第一顺位修复点。**

条款 `parentClauseId` 在 `ClauseQueryResult:39` 与 `ClauseVO:43` 均已存在且由 `toResponse` 正常映射（`ClauseWebMapper:56` 的 ignore 仅作用于 `toCreatedVO` 创建回显路径，语义正确），前端 `types/business.d.ts` 却无该字段 ⇒ 属 §三 #3 同类的"数据已到、UI 未画"。

### 4.3 规则引擎版本化（版本号是装饰性的 — W3/I3）

- **有版本字段无版本演进**：`RuleSet` 仅 4 个命令（Create/AddRule/Activate/Deactivate），`AddRuleCommand` 非 DRAFT 即拒（`RuleSet.java:106-110` 注释「已发布或已退役的规则工件不可修改」），且 `Deactivate` 后不可再激活（`list/index.vue:49-52` 前端注释已确认此状态机）⇒ **一个 (code) 只能有一个 ACTIVE，无法为既有规则集派生 V2.0**。
- **版本号手输**：创建表单 `rule-engine/list/index.vue:66` 是自由 `el-input`，后端 `isBlank` 时回落 `DEFAULT_VERSION="V1.0"`（`RuleSet.java:71-73`），无格式校验、无递增逻辑。
- **执行侧版本钉扎不对称（最危险）**：定价工件计算按 (code,version) 精确解析并校验 ACTIVE + artifactHash + inputSchemaVersion（`RuleExecutionApplicationService.java:200-220`）——**强版本语义**；
  而 `loadCurrentRuleSet` 走 `findByRuleSetCode`，实现是 `findFirstBy...AndStatusOrderByCreateTimeDesc(code, tenantId, ACTIVE)`（`RuleSetRepositoryImpl.java:41-45`）——**"最新 ACTIVE"语义**。
  该路径被 `/execute`、`/validate`、`/score-card`、`/compute` 四个端点共用，也是 underwriting 域 `RuleEngineServicePort.executeRuleSet(tenantId, ruleSetCode, ...)` 的落点（`port/ruleengine/RuleEngineServicePort.java:26`，**签名无版本参数**）。
  ⇒ 核保/理赔/保全链路**无版本钉扎**：新建并激活同 code 的新版本，线上核保行为即静默切换；且 `RuleSet` 无生效期字段，无时间维度可辩护。

### 4.6 无"全部版本列表"端点 + `findByProductCode` 隐患（W4）

- 三处（product-web / clause-web / admin-bff）grep `/versions`、`versionHistory`、`getVersions` **均 0 命中** ⇒ 无法列出"产品 P 的全部版本"。唯一线索是逐条链式 `originalProductId`，而它连 UI 都没画。
- 隐患：`ProductViewRepository.java:34` 声明 `Optional<ProductView> findByProductCodeAndTenantId(...)`。`t_product_view.product_code` 建的是**普通 KEY 非 UNIQUE**（`product_view_202607091700_weisun_ddl.sql:33`），而修订**继承同一 productCode**（`InsuranceProduct.java:298`）⇒ 产品一旦修订出第二个版本，`ProductQueryServiceImpl.java:60` `findProductByCode` 将抛 `IncorrectResultSizeDataAccessException`。该路径可达（`ProductQueryAppService.java:72 queryProductByCode`）。**未证实**：该端点是否有前端调用方（前端 `api/product.ts` 未见按 code 查询），故当前未暴露为用户可见故障，但属版本化引入的确定性缺陷。

### 4.7 审计留痕（B3 / W5 / I1 / I2）

**B3 证据**：`grep -rc "@OperationLog" controller/proxy/` → 19 个代理 Controller **全部为 0**；全仓注解仅 21 处，分布于 `DictController(7)`、`AdminUserController(5)`、`MenuController(3)`、`TenantController(3)`、`RoleController(3)`。
无全局兜底：`config/EndpointAuthorizationInterceptor.java` 不含任何 `OperationLog` 写入（grep 0 命中）。
⇒ **产品修订/发布/退役、费率表校验/发布/退役、定价包审批/发布/退役、规则集激活/停用、条款审批/启用，在管理台操作日志中全部无记录。**

**W5 证据**：`t_operation_log` 表**有** `request_param`/`response_result` 两列（`OperationLogDO.java:56,60`），
但 `OperationLogAspect.saveLog` 的 builder 链（`:93-101`）**只 set requestParam，从不 set responseResult**；
且 `OperationLogVO` 两个字段**都不包含**，前端详情对话框仅展示 username/ip/module/action/duration/status/时间/URL 八项（`system/log:67-84`）。
⇒ 即便系统管理模块，也只能看到"谁点了什么"，看不到"改成了什么值"，更没有字段级 before/after。

**I1 样板**：保全配置域已实现完整的时间线留痕，可原样复制——
后端 `configuration.getAuditTrail()` → `MaintenanceConfigurationWebMapper.java:184,254-256` → `MaintenanceConfigurationVO.java:113 (LifecycleAuditVO)` → BFF `MaintenanceConfigurationMirror.java:41` → 前端 `api/maintenance.ts:360` → `views/maintenance/configuration/index.vue:88-90`（`el-timeline`，含 `action/operatorId/occurredAt/detail`）。

### 4.8 产品模板无版本（W6）

模板决定出单模式/核保策略/理赔流程/保全规则（模块 CLAUDE.md §4.2），属**产品工厂级底座**，其变更不可追溯与不可回滚的风险高于单个产品实例。
