## 一、结论摘要

**一句话**：全站 74 处 `el-dialog` 对 26 处 `el-drawer`、仅 2 处 `el-steps`，形态选择整体**过度弹窗化**——本应用最重的三类配置（计算模型有向图、定价包 17 字段、费率行批量表）都塞在 `<el-dialog>` 里，而唯一的产品"编辑"入口指向一个**永远执行新建**的向导（提交即产生重复产品），规则集"新建"按钮引导用户离开填了一半的大表单且返回后**下拉无法刷新**（必然丢失全部未保存配置），三个不可逆资金动作靠 `ElMessageBox.prompt` 收金额且空输入被静默当作 0 元。

## 三、分级发现明细

### BLOCKER（4 条）

#### B1 产品列表「编辑」打开的是永远执行新建的向导 → 提交即产生重复产品

- **现象**：产品列表点「编辑」→ 进入 `/product/create?id=xxx` 的 5 步向导；向导标题显示「编辑产品」、提交按钮显示「保存修改」，但整页**没有任何产品加载逻辑**，表单是空的；提交时**无条件调用 `createProduct`**。
- **证据**：
  - `src/views/product/list/index.vue:121-123` — 「编辑」按钮带 `v-permission="'product:edit'"`，`@click="goEdit(row.id)"`
  - `src/views/product/list/index.vue:258` — `const goEdit = (id: string) => router.push(\`/product/create?id=${id}\`)`（全仓**唯一**一处带 query 的路由跳转，`grep -rn "route.query\|router.push(.*?" src/views` 仅此命中）
  - `src/views/product/create/index.vue:6` — `{{ isEdit ? '编辑产品' : '新建产品' }}`；`:473-474` — 按钮文案 `{{ isEdit ? '保存修改' : '创建产品' }}`
  - `src/views/product/create/index.vue:535` — `const isEdit = computed(() => !!route.query.id)`（README 级"看起来支持编辑"）
  - `src/views/product/create/index.vue:856-878` — `handleSave()` 仅有 `firstInvalidStep()` 校验，`:872` 无条件 `await createProduct({ ...form, createdBy: userStore.displayName })`，`:873` 提示「创建成功」；全文件**无 `onMounted`**、无 `getProductDetail` 调用（grep 证实）
  - 对照：正确的改产品路径确实存在 —— `src/views/product/detail/index.vue:283` `goRevise = () => router.push(\`/product/revise/${route.params.id}\`)`；`src/views/product/revise/index.vue:465-466` `onMounted` 按 `route.params.id` 加载、`:457` `reviseProduct(route.params.id, buildPayload())`；路由 `src/router/dynamicRoutes.ts:42-45`（`product/revise/:id`，权限同为 `product:edit`）
- **影响**：运营点「编辑」看到一片空白的向导（还以为是数据加载失败），标题与按钮都写着"编辑/保存修改"，提交后**新建出一个重复产品草稿**。用户全程以为自己在改老产品——这是最典型的"说不清自己干了什么"的错误。且因权限一致（同为 `product:edit`），该错误对所有有编辑权的角色都开放。
- **改法**（推荐照抄本仓已有范式）：
  1. `product/list/index.vue:258` 改为 `router.push(\`/product/revise/${id}\`)`（或先跳详情页 `product/detail`，与渠道/用户/菜单/租户的"编辑"一致）。`product:edit` 恰好是 revise 路由的权限，无需改权限。
  2. 删除 `product/create` 里的 `isEdit` 假分支（`:6`、`:473-474`、`:535`、`:528`），使向导只表达"新建"，避免留下"看起来支持编辑"的入口；
  3. 若产品域确实需要"编辑草稿"，则在 `product/create` 补 `onMounted` 按 `route.query.id` 加载 + `handleSave` 分流 `updateProduct/createProduct`，**两者不可只做一半**。

#### B2 规则集「新建」把用户送出填了一半的大表单，回来后下拉拿不到新建结果

- **现象**：产品配置页（7 tab，全量草稿）每个 tab 顶部都有「新建规则集」，点击后 `window.open` 打开新标签页；本页的规则集下拉**只在 `onMounted` 加载一次**，页内没有任何刷新入口。用户在新标签页建好规则集，回到原页发现下拉里选不到，且**刷新才能拿到 → 丢光全部未保存配置**。
- **证据**：
  - `src/views/product/template-config/index.vue:96`、`:129`、`:175` — 三处「新建规则集」按钮 → `openRuleSetPage()`
  - `src/views/product/template-config/index.vue:591-594` — `openRuleSetPage()` 实现为 `window.open(href, '_blank', 'noopener')`
  - `src/views/product/template-config/index.vue:588` — **代码注释自认**"本页是填了一半的产品配置大表单，当前页跳走会丢失全部未保存输入"（所以选择开新标签）
  - `src/views/product/template-config/index.vue:600` — `loadRuleSets()` 仅在 `onMounted` 调用；全文件 grep 无其他调用点，也无"刷新"按钮
  - `src/views/product/template-config/index.vue:339-342` — 单个「保存配置」按钮；`:642-665` — payload 汇总全部 tab 的配置对象；`:341` — `$router.back()` **无未保存拦截**（无 `onBeforeRouteLeave`）
- **影响**：按界面**自己的引导**操作（按钮是新标签页，注释也承认这是为了保草稿）→ 建完规则集却选不上；用户唯一出路是刷新页面，而这正是注释担心的"丢失全部未保存输入"。这是一个**闭环死路**：界面的每一步都在把用户推向丢数据的结局。规则集是产品配置的必填项（费率规则 tab），等于该 tab 在建好规则集前无法完成。
- **改法**：
  1. 规则集创建改在**当前页 `el-drawer` 内联完成**（复用 `rule-engine/list/index.vue:62` 已有 4 字段 + `:101` 表单逻辑），创建成功后 `await loadRuleSets()` 并把新规则集自动选中——拔掉 `window.open` 的根因；
  2. 若短期不能内联，至少补两件：页内「刷新规则集」按钮 + `onBeforeRouteLeave` 未保存确认（`dirty` 标记）；
  3. 「保存配置」改按 tab 差量提交（见 W7），让"填了一半也能存"。

#### B3 三个不可逆资金动作靠 `ElMessageBox.prompt` 收金额：无校验、空输入静默为 0 元、对所有保单无条件可见

- **现象**：保单详情「更多」下拉里，红利派发 / 启动年金给付 / 满期给付三个**出钱**的动作，用单行 `ElMessageBox.prompt` 收集金额；没有 `inputValidator`、没有上下限、没有精度约束、没有二次回显；且这三个动作在下拉里**对所有保单无条件显示**。
- **证据**：
  - `src/views/policy/detail/index.vue:17-52` — 动作下拉 10 项（suspend/resume/terminate/cancel/waive/dividend/annuityStart/annuityPay/mature/endorsement），**仅 suspend / resume / cancel 有 `v-if` 状态门控**；红利/年金/满期无任何门控（寿险专属动作出现在非寿险保单上）
  - `src/views/policy/detail/index.vue:315-322` — `case 'dividend':` → `:316` `await ElMessageBox.prompt('请输入本年度红利金额（元）', '红利派发', { inputType: 'number' }).then(({ value }) => doAction(... dividendAmount: Number(value) ...))`
  - `src/views/policy/detail/index.vue:324-331` — `case 'annuityStart':` → `:325` `prompt('请输入每期年金给付金额（元）', '启动年金给付', ...)` → `amountPerInstallment: Number(value)`
  - `src/views/policy/detail/index.vue:336-339` — `case 'mature':` → `:337` `prompt('请输入满期给付金额（元）', '满期给付', ...)` → `maturityBenefit: Number(value)`
  - 三处均无 `inputValidator`（对比，同仓 `system/user/index.vue:198-201` 的重置密码 prompt 是**有** `inputValidator` 的）；空输入时 `Number('') === 0`；`policy/detail` 全文件 `v-permission` 命中数为 **0**
- **影响**：金额是这三个动作的**唯一业务参数**，却由用户在一个没有校验的单行框里手打。误触回车 → 按 **0 元**派发红利/启动 0 元年金/0 元满期给付，全部不可逆（资金已出账）。同时下拉里所有保单都能看到寿险专属动作，用户没有"这个动作现在能不能用"的提示，只能靠点了之后被后端拒绝来学习。
- **改法**：
  1. 三个动作改**结构化两步确认**：第一步 `el-dialog` 内用 `el-input-number`（`:min`/`:precision="2"`/`:max` 上限）+ `el-form` rules（必填、>0），并展示保单号/被保险人/险种；第二步 `el-alert type="warning"` 回显「确认按 ¥X.XX 向 XXX 派发 2026 年度红利？」，`confirmButtonClass: 'el-button--danger'`（同文件 `:162-176` 的退保弹窗已是此范式，直接复用）；
  2. `:17-52` 补齐产物线/状态门控（把 `dividend/annuityStart/annuityPay/mature` 纳入 `v-if`），并给不可用项以 disabled + tooltip 说明原因（契约第 27 行）；
  3. `:312` 保费豁免的确认文案补后果（"豁免后不再收取后续各期保费"），`type: 'info'` 改 `'warning'`（见 W12）。

- **改法**：统一走 `confirmAction`（`useRowAction.ts:97-108` 返回 boolean，无需 catch，取消分支显式），把 `globalError` 的吞异常降级为安全网而非依赖；否则每新增一个裸调 confirm 就多一处"取消也可能继续执行"的风险面（`ConfigPanel.vue:376-377` 的注释已记录过一次同类事故：`.catch(() => null)` 吞掉取消后仍执行删除）。
