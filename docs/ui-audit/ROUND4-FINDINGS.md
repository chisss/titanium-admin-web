## §0 本轮的一句话结论

**键盘焦点可见性存在四层系统性失效，其中「侧边栏主导航键盘完全不可达」违反 WCAG 2.1.1（A 级）；已全部修复，修复后全站焦点环 10.51~16.49:1。**
**修复的代价（到内容区的路径由 0 格增至 23 格）已用 Skip Link 补偿，实测压回 3 次按键。**

样式侧的问题不是「令牌不够用」而是「**令牌有档不用**」——**84.3% 的写死字面量，其值与**同族**某个已定义令牌完全相等**
（字号 51/54、间距 137/171、字重 22/23）；**22 个令牌引用次数为 0**，
其中 10 个属「有档不用」（它们的值被手写了 50 次）、6 个属真死令牌、6 个属「机制上无法被引用」。

交互侧的结论同样是「**抽象建了但没被消费**」——**102 个写操作调用点中 35 个（34.3%）无任何 pending 反馈**，
**这是交互侧唯一的活跃缺口**；破坏性动作经判据订正后为 **1/18 真缺口（已修）**，原报的 3 处中有 2 处实为误判；

## §一 根因 R1：`:where()` 特异性恒为 0，全局兜底规则被 EP 全面覆盖

### 证据链（三步对照，把「规则写错」与「规则被覆盖」分开）

`src/assets/styles/index.scss:91` 的全局兜底：

```scss
:where(a, button, input, select, textarea, summary, [tabindex]):focus-visible {
  outline: 2px solid $primary-color;   // #1a3a6b
  outline-offset: 2px;
}
```

同一份规则，在四种上下文里实测：

| 场景 | EP 是否有竞争规则 | 实测描边 | 对比度 | 结论 |
|---|---|---|---|---|
| 裸 `<button>`（探针注入） | 无 | `2px solid rgb(26,58,107) off=2px` | 11.28:1 | **本项目规则生效且达标** |
| `.el-dropdown-menu__item` | 无 | `2px solid rgb(26,58,107) off=-2px` | **9.44:1 ✓** | **本项目规则生效且达标** |
| `div.topbar__user` | 无 | `2px solid rgb(26,58,107) off=2px` | **10.51:1 ✓** | **本项目规则生效且达标** |
| `.el-button`（全站 303 个） | **有** | `2px solid rgb(141,157,181)` | **2.57~2.75:1 ✗** | 被 EP 覆盖 |

**⇒ 规则本身写得对（品牌色、9.44~11.28:1），失效的唯一原因是 `:where()` 把它压到特异性 0，而 EP 对几乎每个交互组件都自带 `:focus-visible`（特异性 0,1,0~0,4,0）。**

### 代码注释本身记录了这次误判

`index.scss:83-84` 原文：

> 兜底选择器用 `:where()` 把特异性压到 0，这样各组件自带的更具体规则仍能覆盖它，
> 只在没有任何规则接管时才生效

作者**知道**并**故意**这么做，但「只在没有任何规则接管时才生效」这个前提不成立——EP 几乎处处接管。于是「兜底」等价于「永不生效」。

**这是本轮的第一类「静默失效」**：规则写对了、构建没报错、守卫没命中，只是在层叠里永远输。

## §二 根因 R2：EP 的焦点环取 `--el-color-*-light-5`，在白底上系统性低于 3:1

按按钮类型逐一实测（真实 Tab 遍历，非脚本 focus）：

| 元素 | 焦点环色 | 背景 | 对比度 | WCAG 2.4.11 (≥3:1) |
|---|---|---|---|---|
| `.el-button--success`（启用） | `rgb(179,225,157)` | `rgb(255,255,255)` | **1.42** | ✗ 最差 |
| `.el-button--success`（启用） | `rgb(179,225,157)` | `rgb(250,250,250)` | **1.48** | ✗ |
| `.el-button--danger`（禁用） | `rgb(250,182,182)` | `rgb(255,255,255)` | **1.69** | ✗ |
| `.el-button--danger`（禁用） | `rgb(250,182,182)` | `rgb(250,250,250)` | **1.62** | ✗ |
| `.el-button--primary`（搜索） | `rgb(141,157,181)` | `rgb(255,255,255)` | **2.75** | ✗ |
| `.el-button`（重置/编辑） | `rgb(141,157,181)` | `rgb(255,255,255)` | **2.75** | ✗ |
| `.el-button.is-text`（收起侧栏） | `rgb(141,157,181)` | `rgb(245,247,250)` | **2.57** | ✗ |

**机理**（EP `dist/index.css` 源码）：

```css
.el-button             { --el-button-outline-color: var(--el-color-primary-light-5); }
.el-button--success    { --el-button-outline-color: var(--el-color-success-light-5); }
.el-button--danger     { --el-button-outline-color: var(--el-color-danger-light-5); }
.el-button:focus-visible { outline: 2px solid var(--el-button-outline-color); }
```

「主色压到 light-5」用作**背景/边框**是合理的设计系统手法，但用作**焦点环**时，
浅色在白底上天然不达标。5 种按钮色（primary/success/warning/danger/info）全部如此。

其中 `--el-color-primary-light-5` 经项目 `:root:root` 覆盖为 `mix(#fff, #1a3a6b, 50%)`
= `rgb(140.5, 156.5, 181)`，即上表实测的 `rgb(141,157,181)`。

⚠️ 且这些变量声明在 **`.el-button--X` 类作用域**上（非 `:root`）——
从 `:root` 覆盖会**静默失效**（与第三轮记录的 `--el-table-header-text-color` 同族）。

### 订正：`.el-input__wrapper` 不是缺陷

初测曾把 `.el-input__wrapper` 记为 `rgb(143,157,181)` / 2.74:1 ✗。**本轮复测证伪**：

```
INPUT.el-input__inner  shadow rgb(26,58,107) @el-input__wrapper 压 rgb(255,255,255) = 11.28:1 ✓
```

EP 的 `.el-input__wrapper.is-focus` 走的是 `--el-input-focus-border-color`（默认继承
`--el-color-primary`），**不是** light 阶梯，本就达标。初测数据来源不明，**作废**。

`index.scss:96-109` 中一段注释曾据此声称「EP 自带焦点指示为近黑 #303133、满足 2.4.7」，
同属未经核实的描述，已在本轮改为实测值（浅灰蓝 1px inset、2.74:1 的**未聚焦→聚焦**变化
满足 AA，不满足 AAA），结论「不加轮廓」保留但论据已更正。

## §三 根因 R3：焦点色与「选中态背景」同源 → 1:1 完全不可见

| 位置 | 焦点环 | 描边压到的背景 | 对比度 |
|---|---|---|---|
| 侧边栏**激活**菜单项（数据看板） | `rgb(26,58,107)` | `rgb(26,58,107)` | **1:1 ✗✗** |
| 分页器**当前页**页码 | `rgb(26,58,107)` | `rgb(26,58,107)` | **1:1 ✗✗** |

**共同机理**：两者都命中项目规则，描边取 `$primary-color` = `rgb(26,58,107)`；
而这两个元素的**选中态背景恰好也是 `rgb(26,58,107)`**（同一品牌色）；
再加 `outline-offset: -2px` 使描边画在元素**内部**，于是描边色 = 背景色，**100% 不可见**。

> 注：这不是「浅色底 vs 深色底」问题，而是**焦点色与选中态背景同源**问题——
> 固定焦点色与「用品牌色表达选中」的设计直接冲突。
> **判据**：凡「用背景色表达选中」的组件，其焦点环都不能沿用同一个品牌色。
> 修法是**按上下文换色**（侧栏/分页当前页改白色），而不是全局改焦点色。

## §四 根因 R4（本轮最深）：EP 的 CSS 被打包两份，按需副本**运行时后加载**，推翻一切「同特异性 + 后加载」覆盖

### 现象

分页器的项目覆盖规则**写了、进了产物、文本顺序也对**，真机却读到 EP 的原值：

```
产物 CSS 文本顺序（看着是对的）：
  .el-pager li:focus-visible{outline:1px solid var(--el-pagination-hover-color);outline-offset:-1px}   ← EP
  .el-pager li:focus-visible{outline:2px solid #1a3a6b;outline-offset:-2px}                              ← 项目

真机 computed：outline: 1px … off=-1px   ← 项目规则静默失效
```

### 定位

只有 `document.styleSheets` 才暴露真相——同一份 EP 规则**存在于两个 sheet**：

```
[index-ChSkhHtr.css]  .el-pager li:focus-visible {outline: 1px solid …}   ← EP 全量（主 CSS）
[index-ChSkhHtr.css]  .el-pager li:focus-visible {outline: 2px …}         ← 项目覆盖
[index-D1hz2rFK.css]  .el-pager li:focus-visible {outline: 1px solid …}   ← EP 按需副本，**后加载**
```

`index-D1hz2rFK.css`（51 条，是 `el-pagination` 组件的按需 CSS）由**入口 JS 在运行时
`import`**，因此它在主 `<link>` 之后才注入，**把项目规则又覆盖了回去**。

### 成因

`vite.config.ts` 同时做了两件事：

| 位置 | 做了什么 | 后果 |
|---|---|---|
| `main.ts:6` | `import 'element-plus/dist/index.css'` | EP 全量 CSS 进主 CSS |
| `vite.config.ts` | `ElementPlusResolver()` 默认 `importStyle: true` | **又**按需引入每个组件的 CSS |

EP 样式因此被打包两份。又因 `manualChunks` 把 `element-plus` 主包单独拆出，按需引入的
`element-plus/es/components/{name}/style/css` 是独立模块 → 单独成 chunk → **运行时后加载**。

### 为什么它极难发现

1. **产物文本顺序正确**——`grep` 产物 CSS 看到的是「EP 在前、项目在后」，完全符合预期；
2. **构建无警告**——重复 CSS 不触发 rollup 任何提示；
3. **只在运行时暴露**——必须枚举 `document.styleSheets` 才能看到一个多出来的 sheet；
4. 症状**因组件而异**：`.el-button` 的覆盖生效、`.el-pager li` 的失效，看起来像「选择器写错」。

### 修复（根治）

```ts
// vite.config.ts
ElementPlusResolver({ importStyle: false })   // AutoImport 与 Components 两处都要加
```

项目既然已全量引入 EP 样式，按需引入的组件 CSS 就是**纯冗余**。关掉后：

| 指标 | 修前 | 修后 |
|---|---|---|
| 产物 CSS 文件数 | 63 | **41** |
| 含 `:focus-visible` 覆盖冲突的 sheet | 2 | **1** |

组件样式完好性抽查（真机 computed，确认无样式丢失）：

```
表格底边框       rgb(96, 98, 102)              ✓
表头背景         rgb(255, 255, 255)            ✓
主按钮底色       rgb(26, 58, 107)              ✓ 品牌色
下拉 wrapper 阴影 rgb(220, 223, 230) 0 0 0 1px inset ✓
分页容器 display  flex / item minWidth 32px    ✓
输入 wrapper 阴影 rgb(220, 223, 230) 0 0 0 1px inset ✓
```

> 🔴 **通用教训**：任何「同特异性 + 后加载」的覆盖策略，其成立前提是**被覆盖方只加载一次**。
> 当同一份第三方 CSS 存在多份副本、且副本加载时机不受控（懒加载 chunk、运行时 import）时，
> 该策略随时可能被静默推翻。**这类失效在文本层面不可见，必须用 `document.styleSheets` 验证。**

## §五 最严重缺陷：侧边栏主导航键盘完全不可达（WCAG 2.1.1，A 级）

### 实测（修复前）

| 指标 | 实测值 |
|---|---|
| `.el-menu-item` 数量 | **31**，`tabindex` **全部为 -1** |
| `.el-sub-menu` 数量 | **14**，**无 `tabindex` 属性** |
| 可 Tab 的菜单项数 | **0** |
| 菜单项标签 | `LI`，**无 `href`** |
| 真实 Tab 前 12 格中侧栏内元素出现次数 | **0** |

真实 Tab 顺序（`/dashboard`，前 12 格）：
`BUTTON → BUTTON → DIV.topbar__user → DIV.ti-page → BUTTON → INPUT → BUTTON → BUTTON → BODY → BUTTON → BUTTON → DIV.topbar__user`
——**侧边栏一个元素都没进入焦点序列**。

### 成因

`src/layouts/components/Sidebar.vue:25` 的 `<el-menu router>` 使 EP 用 `<li>` + JS 跳转渲染，
**不是 `<a href>`**，故既不可 Tab 也不可被辅助技术识别为链接。

且 **EP 的 `el-menu` 在垂直模式下不提供任何键盘支持**——其 `menu-item.vue…mjs:66` 硬编码
`tabindex: "-1"`，模块内无 keydown 监听、无方向键处理（唯一的 `ArrowDown` 是图标导入）。

### 连带死规则

`.el-menu-item:focus-visible`（`index.scss:117`）因菜单项永不获得焦点而**永不匹配**——
与 `.el-table__body tr:focus-visible`（`tr` 无 `tabindex`，实测 `hasTabindexAttr: false`）**同族**。

**死规则合计 2 条**，均为「规则写了、元素不可聚焦」。这类规则在构建、守卫、人工 review 中都不会报错。

### 修复

`Sidebar.vue` 三处补丁：

1. **`tabindex="0"`**：菜单项与子菜单（Vue 会把非 prop 的 attrs 透传到 `el-menu-item`/`el-sub-menu`
   的根 `<li>`）。子菜单的 `tabindex` 落在根 `<li>` 上，视觉焦点用 `:deep(… > .el-sub-menu__title)`
   把描边画到标题行。
2. **`@keydown` 事件委托**挂在 `<el-menu>` 上：Enter / Space 复用 EP 自身的 click 处理
   （菜单项走 router、子菜单走展开），不重复实现分支。`preventDefault()` 阻止 Space 的默认滚动。
3. **焦点环换色**：深底上不能沿用品牌色（§三），改用 `$sidebar-active-text`（白）。

⚠️ **必须同时抑制 `<li>` 自身的环**：`li` 一旦有了 `tabindex` 即匹配 `index.scss:91` 的全局兜底
`:where(…, [tabindex]):focus-visible`（EP 对 `.el-sub-menu` 无焦点规则，兜底得以生效），
品牌色压在侧栏深底上实测仅 **1.46:1**；且子菜单展开时该环会圈住整个展开组。故：

```scss
:deep(.el-sub-menu:focus-visible) { outline: none; }                       // 抑制 LI 自身的环
:deep(.el-sub-menu:focus-visible > .el-sub-menu__title) { outline: 2px solid $sidebar-active-text; outline-offset: -2px; }
```

### 修复后实测

| 指标 | 修前 | 修后 |
|---|---|---|
| 菜单项 `tabindex` | 31 个全 `-1` | **31 个全 `0`** |
| 子菜单 `tabindex` | 14 个全无 | **14 个全 `0`** |
| Tab 进入侧栏 | 前 12 格 0 次 | **第 1 格即 `LI.el-menu-item "数据看板"`** |
| Enter 激活 | — | **`/system/user` → `/dashboard`，URL 真实跳转 ✓** |
| 菜单项焦点环 | 不可达 | **2px 白 off=-2px 压 rgb(15,30,61) = 16.49:1** |
| 激活项焦点环 | — | **2px 白 off=-2px 压 rgb(26,58,107) = 11.28:1** |
| 子菜单标题焦点环 | 不可达 | **2px 白 off=-2px = 16.49:1**（LI 自身 `outline:none` ✓） |

### 副作用评估：侧栏停靠点

修复后侧栏进入 Tab 序列，实测**占前 22 格**（31 菜单项中未展开者的子项 `display:none` 不可 Tab）。
这是一个真实的可用性代价：键盘用户需按 22 次才能抵达内容区。

> **已在本轮处理**（§11.1 第 ⑥ 项）：加 Skip Link，实测**23 次 Tab → 3 次按键**
> （`Tab` 聚焦链接 → `Enter` 跳转 → `Tab` 落到内容区第一个控件）。
> 之所以要做——22 格**不违反**任何 WCAG 条款（故不是「缺陷」），但它是**我们自己引入的代价**：
> 修复前侧栏根本不可聚焦，到内容区是 0 格；修复后变 22 格。**改动方应对自己引入的代价负责。**
>
> roving tabindex（整组只占 1 格、内部方向键）能把 22 格压到 1 格，收益更大，
> 但需自实现方向键导航（EP 不提供），属独立改造，见 §11.1 ⑥ 的取舍记录。

### 附带修正：滚动容器不再占位

修复前 Tab 第 1 格曾是 `DIV.el-scrollbar__wrap`（浏览器默认 `1px auto rgb(0,95,204)`，
与全站 2px 品牌色环风格不符）。修复后实测该容器 `tabindex` 为 `null`、**不再进入焦点序列**，
首格直接是第一个菜单项——该瑕疵随修复消失。

## §六 修复后真机复测原始数据（`/system/user`）

判据（沿用 §七 方法论）：`outline-offset >= 0` 压**父元素**背景，`< 0` 压**元素自身**背景。

| # | 元素 | 焦点环 | 压到的背景 | 对比度 |

## §七 探针方法论（本轮踩到并修正的坑，均可复现）

| 坑 | 现象 | 修正 |
|---|---|---|
| ① 页面非预期状态 | 导航 `/login` 被守卫重定向回 `/dashboard`，两页数据**完全雷同**却未报警 | 每次导航后断言 `location.pathname` 与预期一致 |

| ⑤ **背景取错层** | `outline-offset: 2px` 的实心主按钮被判成「压自身品牌色背景 = 1:1」 | 按 offset 正负**分别取父元素 / 自身**背景；`>=0` 时必须从 `parentElement` 起找 |
| ⑥ **只信产物文本、不看运行时** | 产物 CSS 里项目规则明明在后，真机却是 EP 的值（§四） | 覆盖类断言**必须查 `document.styleSheets`**，文本顺序不是判据 |
| ⑦ **拿会被压缩的标识符当判据** | `grep handleMenuKeydown dist/` 找不到 → 误判「补丁没进产物」 | production build 会 minify 局部函数名；改用**字符串字面量**（`tabindex:"0"`、`"Enter"`）判定 |
| ⑧ **复测对象不是当前工作树** | 改完代码真机验证全无变化——`dist/` 是两天前的旧产物，8888 由 Docker(nginx) 提供 | 复测前先核对**产物与工作树的一致性**（时间戳 + 特征字符串），不能只看「服务在跑」 |

不可作为判据。本报告 §一~§六 的全部焦点数据均用**真实 Tab 遍历**取得。

**坑⑧ 是本轮最贵的教训**：`docker cp` 只覆盖不清理，本地 `dist/` 的残留文件会被一并搬运，
而页面可能仍引用它们——「复测通过」与「复测的是新代码」是两件事。

### 8.2 破坏性操作的二次确认：3/18 零确认 → **订正为 1/18**（判据错位）

按函数名判定破坏性（`delete|remove|terminate|cancel|retire|deactivate|reject|revoke|suspend|disable|close|stop`），
共 18 个调用点，15 个「有确认」。**当时的判据是「有没有调 `ElMessageBox.confirm`」**，
据此报出 3 个零确认。逐一回看代码后，这个判据**数错了对象**——它量的是**确认的机械形式**，
不是**用户有没有被告知后果**：

| 页面 | 行 | 调用 | 当时判定 | 实际（回看代码） |
|---|---|---|---|---|
| `policy/detail/index.vue` | 360 | `suspendPolicy` | 🔴 零确认 | ✅ 有专用对话框（必填中止原因）+ 可逆（同页有 `resumePolicy`）⇒ **不是缺陷** |
| `policy/detail/index.vue` | 375 | `terminatePolicy` | 🔴 零确认 | ✅ 对话框内**已有** `el-alert type="warning"`「退保后将扣除手续费…**操作不可撤销**」⇒ **不是缺陷** |
| `claim/detail/index.vue` | 459 | `rejectClaim` | 🔴 零确认 | 🔴 **确认是真缺口**：对话框只有原因选择，**无任何不可逆提示**，而 `REJECTED` 无回退操作 |

> 🔴 **与 8.4「禁用账号」的区别恰恰在判据上**：那处是真·零确认——点了就锁死，
> 既无对话框也无提示，所以补 `ElMessageBox.confirm` 是对的。而这三处**已经有了表单对话框**，
> 用户是「打开对话框 → 填原因 → 点确认」三步操作，本身即是确认步骤；
> 再叠一层 `ElMessageBox.confirm` 会变成**确认套确认**，属于机械补丁。
>
> **正确的判据不是「有没有调 confirm」，而是「破坏性 + 不可逆的操作，用户有没有被告知后果」。**
> 按此判据，`terminatePolicy`（有 warning 提示）达标，`rejectClaim`（无提示）不达标。
>
> **确切的缺口是「同页不一致」**：`claim/detail` 同一页上 `close`（结案）走
> `ElMessageBox.confirm` 并写明「结案后案件不可再变更」，`reject`（拒赔）同属终局却什么也没说。
> 修法应与项目已有范式对齐——`policy/detail` 的 `terminate` 对话框用 `el-alert type="warning"`
> 承载后果说明，本页照此办理（见 §11.1 第 ⑤ 项）。
>
> 教训：**破坏性操作的确认强度，应由「可逆性」这一业务属性决定，而不是由「调了哪个 API」决定。**
> 按 API 名统计会同时产出两类误差——把有对话框的算成零确认（本节 2 处），
> 以及把「有 confirm 但没讲后果」的算成已确认（未在本轮统计中出现，但同一判据的必然盲区）。

### 8.3 失败处置：58/102 无 catch（56.9%）→ **订正：不是活跃缺陷**

| | 调用点数 | 占比 |
|---|---|---|
| ✅ 所在函数有 `try/catch` 或 `.catch()` | 44 | 43.1% |
| 无 catch | 58 | 56.9% |

`api/http.ts` 的响应拦截器已统一 `ElMessage.error` 并 reject 带 `tiErrorHandled` 标记的 Error
（D-501-51），因此**用户仍会看到错误提示**，这不是「静默失败」。

本节初稿据此推断出两条危害，**逐条核实后两条都不成立**：

| 初稿断言 | 核实方法与结果 |
|---|---|
| 「取消确认框 → 未处理 promise rejection → 控制台 `Uncaught (in promise) cancel`」 | 🔴 **已被 D-10 全局兜底覆盖**。`utils/globalError.ts` 在 `app.config.errorHandler`（事件处理器抛出的）与 `window.unhandledrejection`（不经 Vue 的悬空 promise）**两处**吞掉 `'cancel'`/`'close'`，其余一律保持可见。故该噪声早已不存在。 |
| 「状态卡死：reject 后 `saving` 不复位、按钮永久转圈」 | 🔴 **不成立**。两轮独立扫描（`/tmp/scan-stuck.mjs`、`/tmp/scan-stuck2.mjs`）覆盖 `src/**/*.vue` 全部形如 `*loading/saving/submitting/pending/processing/confirmLoading*.value = true` 的位置：**没有一处缺 `finally` 复位**（第一轮判据：置 true 到复位之间是否含 `finally`，0 命中；第二轮判据：按文件核对 `= true` 与 `= false` 的出现次数，0 命中）。 |

**那么 58 个裸 `await` 的真实性质是什么？** 逐一核实其外层语境（`/tmp/scan-mb.mjs`，
判据：该调用是否位于某个 `try` 块内、其 `catch` 是否会拿到这个 rejection）：

- **41 处调用点，没有一处把「用户取消」误报成错误**——没有一处位于会处理错误的 `catch` 内；
- 其余位于「仅 `finally`」或「裸 `await`」的上下文中。裸 `await` 下控制流本身是**正确的**：
  rejection 会直接中止该 async 函数，后续语句不执行——这正是「用户取消 ⇒ 什么都不该发生」的期望行为。

> 🔴 **教训（本节是本轮第二次同族错误，与 §8.2 同源）**：§8.2 数错了「确认」的对象，
> 本节数对了「有没有 catch」却**没有核实它所声称的危害是否真的存在**。
> **计数型判据有两个必须分别核实的部分：数的对象对不对，以及由该计数推出的危害成不成立。**
> 后者更容易漏——因为计数有 grep 可跑，危害只能靠读代码与实测。
>
> **结论：本节不构成缺陷条目，降级为「实现风格的一致性观察」。**
> 保留 `confirmAction` 化的价值仅在于**把「取消 = false」从全局副作用改写为本地显式控制流**：
> 读代码的人不必先知道 D-10 的存在才能确定取消后的行为。它改善的是可读性，不是用户可见行为。
> 故**不为它单独发起全站批量改造**——把力气留给 §8.1（pending 反馈），那才是用户能感知的缺口。

### 9.1 `el-dialog` 宽度：19 种取值 / 37 个对话框

| 次数 | 取值 | | 次数 | 取值 |
|---|---|---|---|---|
| **10** | `560px` | | 1 | `1180px` |
| 4 | `480px` | | 1 | `620px` / `660px` / `500px` / `460px` |
| 3 | `520px` | | 1 | `min(1180px, 94vw)` |
| 3 | `440px` | | 1 | `min(1100px, calc(100vw - 24px))` |
| 2 | `640px` | | 1 | `min(1000px, calc(100vw - 24px))` |
| 2 | `400px` | | 1 | `min(900px, calc(100vw - 24px))` |

**两处系统性不一致**：

1. **同一量级、两种写法**：`1180px`（裸 px）与 `min(1180px, 94vw)`（响应式）**并存**；

## §十 令牌消费率与美观性

### 10.1 四族令牌消费率

> 🔴 **本节数字来自 `node scripts/ui-guard.mjs --rule=D-15`，不是探针脚本。**
> 首版本节的数字由一次性 python 探针产出，与守卫实现存在**系统性差异**（详见 §11.2「二次订正」）：
> 探针的「命中档位」是**跨族按裸值**比对，于是 `font-size: 20px` 撞上 `$space-5: 20px`
> 被算成「有档不用」——可令牌表里根本没有 20px 的字号档，照它改会把间距令牌用在字号上。
> 现守卫已改为**同族比对**（前缀 `font-size-` / `space-` / `radius-`+`border-radius` / `font-weight-`），
> 本表随之重出。**报告与守卫从此引用同一份数字。**
>
> 判据：解析 `variables.scss` 的全部令牌值，按**语义族**建索引；再普查各 `.vue` 与 `.scss`
> （剔除整行注释与行内注释），把每条 `font-size` / `padding|margin|gap` / `border-radius` / `font-weight`
> 声明分为「引用令牌」与「写死字面量」，并检查字面量的值**在该族内**是否恰好等于某个档位。

| 令牌族 | 引用令牌 | 写死字面量 | 字面量**命中同族档位** | **令牌消费率** |
|---|---|---|---|---|
| `space` | 9 | 171 | 137（**80.1%**） | **5.0%** |
| `font-size` | 22 | 54 | 51（**94.4%**） | 28.9% |
| `font-weight` | 1 | 23 | 22（**95.7%**） | **4.2%** |
| `border-radius` | 13 | 1 | 0（0%） | **92.9%** ✅ |
| **合计** | **45** | **249** | **210（84.3%）** | **15.3%** |

**「字面量命中同族档位」这一列是本轮最关键的发现**：

> **84.3% 的字面量，其值与**同族某个已定义令牌**完全相等。**
> 也就是说，问题**不是「令牌体系设计得不合适」**——如果档位不合用，字面量会落在档位之外；
> 实测 210/249 落在档位**之内**。问题是**开发者在写一个已经在档位上的值时，选择了写字面量**。

`border-radius` 的**消费率**是唯一健康的一族（92.9%），说明**这套机制本身是可用的、也被用过**——
不是工具问题，是习惯问题。（该族的 1 处字面量恰好不在档位上，故「命中档位」列是 0%；
这一列与消费率是**两个不同的量**，不要混读。）

> 🔴 **`font-weight` 的 95.7% 尤其说明问题**：23 处写死的字重里 22 处都是档位内的值，
> 却只有 1 处走了令牌。这一族**几乎没有一个「档位不够用」的借口**——纯习惯。


### 10.2 零引用令牌：22 个令牌「定义了，但全站无人引用」（订正：原报 9）

> 🔴 **订正说明**：原报「9 个」是**探针口径的局限值**——那个探针只统计
> `font-size`/`space`/`radius`/`font-weight` **四族**的零引用。守卫 D-16 扫描**全部 88 个令牌**，
> 得 22 个。两条**互相独立**的实现（守卫的正则提取 + 一次性 node 脚本）复核均为 22，
> 故本节改用 22，并把 22 个**按「为什么零引用」分三类**——它们不是同一类问题，处置方式各不相同。

**① 真·死令牌（6 个仍零引用，建议删除）**

| 令牌 | 值 | 说明 |
|---|---|---|
| `$z-index-dropdown` `-sticky` `-fixed`⚠️ `-modal-backdrop` `-modal` `-popover` `-tooltip` | 1000~1060 | 全站仅 `login/index.vue:210` 一处 `z-index: 1`（局部堆叠上下文，不需要令牌）。EP 的弹层层级由它自己的 `--el-index-*` 管理，**这族令牌没有任何消费场景** |

> 这也说明一个判据问题：**「零引用」是当前状态，不是永久属性**——

> z-index 族里恰有一个（`-fixed`）在我改动布局的当天就被用上了。

**② 有档不用的「消费侧缺口」（10 个，见下表）——这是 §10.1 问题的具体化**

### 10.3 缺档：39 次落在档位之外的值（订正：原报 34）

> 🔴 原报的 «34 次» 混入了**跨族误判**（`font-size: 20px` 曾因撞上 `$space-5` 被算作「有档」），
> 且漏计了 `font-weight 900`。以下为守卫同族比对后的完整列表。

| 族 | 档位外值 | 次数 | 说明 |
|---|---|---|---|
| `space` | `10px` | **10** | 落在 `8px`(`$space-2`) 与 `12px`(`$space-3`) **之间**——档位表缺一档 |
| `space` | `18px` | 7 | 落在 `16px`(`$space-4`) 与 `20px`(`$space-5`) 之间 |
| `space` | `6px` | 6 | 落在 `4px`(`$space-1`) 与 `8px`(`$space-2`) 之间 |
| `space` | `14px` | 5 | 落在 `12px` 与 `16px` 之间 |
| `space` | `2px` / `5px` | 4 / 1 | 微调值，可不入档 |
| `space` | `120px` | 1 | 一次性（AI 聊天区高度），与 `$ai-chat-height` 语义不同，保留字面量合理 |
| `font-size` | `20px` / `24px` | 1 / 1 | 档位表从 `18px`(`xl`) 直接跳到 `22px`(`2xl`)，中间有空档 |
| `font-size` | `120px` | 1 | 登录页品牌大数字，一次性，保留合理 |
| `font-weight` | `900` | 1 | 档位表最高 `700`(`bold`)，缺 `900`；仅 1 处，保留合理 |
| `border-radius` | `16px` | 1 | 档位为 `sm/md/lg` + `$border-radius`，无 16px 档 |

**判据**：出现 ≥5 次的档位外值（`space 10/18/6/14px`）说明**档位表确有缺口**，应补档；
出现 1 次的（`120px`、`900`）属**合理的一次性取值**，保留字面量即可，不必为它建令牌。

> 原报告有一句推断需要收回：「`space` 的 8 档粒度不足以覆盖真实需求」——这句**方向对但结论过强**。
> 实测档位外值集中在 `6/10/14/18px`，确实都在两档之间，**补档是合理的**；
> 但其中 `2px`(×4) 与 `5px`(×1) 属微调，`120px`(×1) 属一次性，
> 为它们建令牌反而会把令牌表撑大而收益为零。**补档的判据应是「该值重复出现 ≥5 次」**，
> 不是「只要落在档位外就补」。

### 10.4 对美观性的实际影响

令牌消费率低**不是洁癖问题**，它有三个可观测的视觉后果：

1. **跨页节奏漂移**：全站正文在 `11px / 12px / 13px / 14px` 之间无规则游走。
   单页内不可辨（1px 差异），但**并排两个列表页时，表格行高与信息密度肉眼可辨地不同**。
2. **层级失效**：§9.6 的区块标题——21 处**根本没声明字号**，它们的外观由父容器决定。
   同一个小节标题，在 A 页是 16px/600、在 B 页是继承来的 14px/400。**视觉层级在结构上存在、在呈现上随机。**
3. **改不动**：想把主力字号从 13px 调到 14px（提升后台可读性的常见诉求），
   需要改 **19 处字面量**，且必须**先确认这 19 处是不是同一个语义**
   ——`$font-size-md` 改名能一次生效，`13px` 出现 19 次则无法区分「表格正文」与「恰好也是 13px 的其它东西」。

### 10.5 与焦点缺陷的关系（本轮两类的共同机理）

§一~§五 的焦点缺陷是「**规则写了但被覆盖**」，
§八~§十 的一致性是「**抽象建了但没被消费**」——
`TiStatusTag` 建了、23 处仍用裸 `el-tag`；令牌定义了、248 处仍写字面量；
`showErrorIfUnhandled` 提供了、调用方仍裸 `ElMessage.error`。

> **共同机理**：项目已经具备正确的抽象，**缺的是让抽象成为唯一路径的约束**。
> 这直接决定了 §十一 的守卫策略——**守卫应当检查「有没有绕开抽象」，而不只是「抽象是否存在」**。

**⑥ 详情（Skip Link）**
| 项 | 实测值 |
|---|---|
| 隐藏手法 | `transform: translateY(-100%)`（未聚焦时 rect `y=-40`，完全在视口外） |
| DOM 位置 | `.app-layout` 首个子元素，**实测为全站第一个可聚焦元素** ✅ |
| 焦点环 | `2px solid #ffffff` + `outline-offset: -2px` ⇒ 白压 `#1a3a6b`(**自身底色**) = **11.28:1** |
| 落点 | `<div id="main-content" tabindex="-1">`，`:focus { outline: none }`（见下方「为何落点不画环」） |
| **端到端** | 保单查询页：`Tab`(聚焦链接) → `Enter`(跳转) → `Tab` ⇒ 直接落到**全序列第 22 个**可聚焦元素（内容区搜索框）<br>即 **23 次 Tab → 3 次按键** |
| 回归 | 侧栏菜单项焦点环仍为白色 2px/-2px；`Enter` 真实跳转到 `/dashboard` ✅ |

> **为什么必须配这一条**：②的侧栏修复给 45 个 `<li>` 补了 `tabindex="0"`，
> 主导航从「完全不可达」变成「可达」，**代价是到内容区的路径从 0 格变成 23 格**。
> ②与⑥是**一对不可分的契约**：只要侧栏还靠 `tabindex` 提供键盘可达，跳转链接就不能删——
> 故立 `A-01` 守卫把两者绑在一起（侧栏一旦改用原生控件，该规则会提示「存在理由需重新评估」）。
>
> **为什么落点容器不画焦点环**：`#main-content` 是整块滚动区（实测 `clientHeight 760`），
> 给它描边会得到一个**撑满视口的框**，读起来像「整个页面被框住了」而不是「焦点在这里」。
> 且容器不是用户「走到」的，只可能是被程序聚焦。**「跳转成功」的反馈由滚动位置变化承担**——
> 这与「焦点必须可见」不冲突：WCAG 2.4.7 针对的是**交互组件**，落点容器不承载交互。
>
> **取舍记录**：另一方案是 roving tabindex（侧栏只留 1 个 Tab 停靠点，内部用方向键走），
> 可把 23 格压到 1 格，但要自己实现焦点管理、`aria-activedescendant` 与子菜单展开逻辑，
> 改动面覆盖整个 `Sidebar.vue`。Skip Link 以约 1/20 的成本拿到大部分收益（跳过来只需 3 键），
> 且是标准做法。**若后续侧栏复杂度进一步上升，roving tabindex 仍是更好的终态。**

### 11.5 本轮的方法论产出（可复用于后续走查）

1. **覆盖类断言必须查运行时 `document.styleSheets`，产物文本顺序不是判据**（§四）；
2. **`:where()` 把特异性压到 0 ⇒ 「兜底」等于「永不生效」**，兜底规则必须验真机（§一）；
3. **焦点色与选中态背景同源 ⇒ 1:1**，凡「用背景色表达选中」的组件都要换焦点色（§三）；
4. **计数型判据必须问它数的是不是我交付的那个东西**——本轮撞了**六次**
   （§七 坑⑤~⑧ + §11.2 + §8.2 的「按 API 名判确认」）；
   🔴 **判据有两个必须分别核实的部分：数的对象对不对，以及由该计数推出的危害成不成立。**
   后者更容易漏——计数有 grep 可跑，危害只能靠读代码与实测。§8.3 正因此把
   「58 处无 catch」当成了缺陷，而它的两条危害（取消噪声、状态卡死）**已被别的机制解决**
   （D-10 全局兜底 / 全部 pending 标志都有 `finally`）。**没核实危害的计数，只是数字，不是发现。**
5. **抽象存在 ≠ 抽象被用**，守卫要查「绕开抽象」而不只是「抽象存在」（§十）；
6. **复测前必须核对产物与工作树的一致性**（§七 坑⑧）；
7. **同族比对 ≠ 跨族按值比对**（§10.1 订正）：判「有档不用」必须限定在同一语义族内，
   否则会产出**错误建议**（把间距令牌用在字号上）——错判比漏判更危险，因为它会指导一次错误的修改；
8. **同一个量只能有一个真源**（§11.3）：报告与守卫、守卫内两条相关规则，
   都必须引用同一份数字。本轮 D-15 与 D-17 曾各算各的，同一份代码报出两个总数（226 vs 272）；
9. **破坏性操作的确认强度由「可逆性」决定，不由「调了哪个 API」决定**（§8.2）；
10. **「零引用」是当前状态而非永久属性**：删令牌前要问「这个语义将来会不会需要」
    （`$z-index-fixed` 在改动布局的当天就被启用）。
11. 🔴 **守卫的可见域由它自己的正则与「强制前缀」决定，看不见 ≠ 不存在**——本轮 I-01
    两次报「全部达标」而实际上探测面是空的：①`<el-button\b[^>]*>` 遇到箭头函数 `=>` 里的 `>`
    会**在属性中途截断标签**（全站 48 个下拉标签只认出 1 个）；②判定写成 `name(` 时，
    分派表 `{ submit: handleSubmit }` 里的**裸引用**让整条链路断在表上（product/list 等三页整体在视野外）。
    **修法是把「引号感知」与「引用式判定」写进规则本身**，并且修完要拿手工点数的真值对账
    （下拉触发器 1 → 6，与人工计数吻合）。
12. 🔴 **一条不会失败的守卫毫无价值——反向验证是必需品，不是加分项**。
    做法固定三步：故意注入回归 → 确认能 FAIL → 原样还原后复测归零。
    本轮 I-01 特意选了**三条不同代码路径**各注入一次（`actionKey` 按钮 / `isRowBusy` 助手 /
    `runRowCommand` 分派表），命中 3/3 且报出正确函数名——只验一条路径只能证明那条路径有牙。
    ⚠️ 注入用的临时改动必须 `cp` 备份后原样还原，不能靠「再改回去」。
13. **计数型判据的第二半：由该计数推出的危害成不成立**（§11.5 第 4 条的延伸，本轮 I-01 再证）：
    同一份「写操作载体清单」，比例型口径（覆盖率 ≥95%）会**用分母掩盖分子**——它既看不见
    「一个按钮同时点亮另一行」这类**归属错误**，也会把「按函数名判」的误报带进来。
    **能用绝对判据（必须为 0）时不要用比例判据。**

### 11.6 契约测试锁「实现形式」会在重构时误报（本轮实例）

`tests/pricing-testcase-contracts.test.mjs:43` 原先断言 `:loading="testRunning"`。
§8.5 把 `testRunning` 这个**全局布尔**收敛为按行键的 `isRowBusy(row)` 之后，
**123 项里 1 项变红**——代码变好了，测试却报失败。

修法是把断言从**实现形式**改为**意图**：

```js
assert.match(source, /const \{ rowPending, run \} = useRowAction/)
assert.match(source, /:loading="isRowBusy\(row\)"/)
```

**教训**：契约测试应当锁「触发器绑定了本行的在途状态」这一**行为意图**，
而不是某个变量名。锁形式只能证明「没被改过」，锁意图才能既保护行为、又不挡改进。
（这与本报告反复出现的「数的是不是我交付的那个东西」是同一问题的另一面：
**前者是判据看不见改进，后者是判据看不见缺陷**。）

### 11.7 守卫 I-01：把「点下去没反应」变成构建期约束

**判据**：模板里 `<el-button @click="fn(…)">`、`<el-switch @change="fn(…)">`、
`<el-dropdown @command="fn">` 的触发器，若 `fn` **能追到写接口**，则该载体必须带 `:loading`。

**「能追到写接口」的三层判定**（`scripts/ui-guard.mjs` 的 `apiWriteFns` / `isWrite`）：

1. 从 `src/api/*.ts` 提取写函数：**函数名动词前缀白名单 ∪ 函数体含 `http.put|delete|patch`**。
   不能只看 `http.post`——本仓读接口大量借 POST 做搜索（`getDictTypeList`、`getTemplate`…）。
2. 页面内在**函数体**里追（**深度 ≤3 的调用闭包**），不是只看模板上写了什么。
3. 判定用「**引用**」而非「调用」：本仓下拉分派统一写成**分派表**
   （`const handlers = { submit: handleSubmit }` 然后 `handlers[cmd]?.(row)`），
   表里是**裸函数引用、没有括号**，只认 `name(` 会让整条链路断在表上。

**🔴 这条守卫自己是怎样两次差点变成「空心绿」的**（两个坑都值得写进方法论）：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| ① | 全站 48 个下拉标签只认出 **1 个**，规则却报「全部达标」 | `<el-dropdown\b[^>]*>` 遇到箭头 `=>` 里的 `>` 会**在属性中途截断标签**，`@command` 与它后面的 `:loading` 一起消失 | 改用引号感知的 `openTagRe()`：`(?:"[^"]*"|'[^']*'|[^>"'])*`；并加 `(?=[\s>])` 免得把 `<el-dropdown-menu>` 算成下拉本体 |
| ② | 补齐标签后仍只有 1 个 | 分派表里的 `handleSubmit` 是**裸引用**，闭包只认 `name(` | 改按「引用本文件已定义的局部函数名」判定（不是任意标识符，且先剥注释控误报） |

两个坑修完后，下拉触发器数从 **1 → 6**，与**手工点数的业务下拉数完全吻合**
（clause/list、configuration、workbench、product/list、pricing-plans、policy/detail）。

**它当场产出的发现**：扫描器（只找「`@click` 里直接写接口名」）漏掉的 **5 处真缺口**——
`billing/commission-payables` 的完成回拨/取消（**不可逆的资金状态推进**）、
`clause/edit` 的责任子表即时删除、`maintenance/configuration` 抽屉的创建修订、
`notification/list` 的批量确认送达、`product/list` 的导出。「守卫只是形式主义」的反例。

**反向验证（关键）**：一条不会失败的守卫毫无价值。故意删掉 3 处 `:loading`
（分别走 `actionKey` 按钮、`isRowBusy` 助手、`runRowCommand` 分派表三条不同路径），
实测**精确命中 3/3** 且报出正确的处理函数名；`cp` 备份原样恢复后复测 0 命中。

**已知盲区（显式写出，避免把「没扫到」当成「不存在」）**：
仅当处理函数**能追到**写接口才判定（闭包深度 ≤3，动态查表不追）；
`el-select` 的 `@change` 即时落库、拖拽排序等非按钮载体不在判据内；
**「有 loading」不等于「loading 归属正确」**——后者静态不可判，只能靠 `actionKey` 的使用纪律。
