## 一、结论摘要

### 1.1 分层结论

本仓金融字段的**控件选型基本正确**（数值字段一律 `el-input-number`，未发现裸 `el-input` 承载普通金额输入），
但**「单位表达」与「结果预览」两项几乎整体缺失**，且存在 **5 处会直接写错资金/费率的缺陷**。

| 维度 | 结论 |
|------|------|
| 控件选型 | ✅ 良好。全站数值字段 104 处 `el-input-number`；仅保全工作台 1 处（高价值）用裸文本 |
| 单位表达 | 🔴 **系统性缺失**。57/68 处金额不传币种；11 处比例字段无 `%` 标记；比例存在 0-1 与 0-100 双编码 |
| 精度控制 | 🟡 有精度但**取值分歧**（同概念 4/6/8 位并存）；5 处比例字段精度与单位不匹配 |
| 范围约束 | 🟡 单值范围尚可；**跨字段范围有校验**（保费区间/年龄区间 ✅）；但无上限的费率字段仍存在 |
| 结果预览 | 🔴 **完全缺失**。0 处试算/预览；定价包仅有「保存后门禁测试」这一事后路径 |
| 格式化复用 | 🔴 **归一化失败**。金额 1 套（`formatAmount`）但 84% 调用不传币种；比例 **8 套**互不相同的实现 |

### 1.3 三条最危险的模式（本报告核心结论）

**① 比例字段存在 0-1 与 0-100 双编码，且 Element Plus 会静默钳制越界输入。**

- 理赔域教用户「比例填百分数」：`claim/config:182` `赔付比例（%）` `min 0 max 100`；`claim/detail:113` 输入框旁带 `<span class="unit">%</span>`，且提交时 `claim/detail:425-426` 做 `percent / 100` 转换。
- 产品/渠道域却用 0-1 编码且**无任何单位标记**：`channel/list:113`、`commission-schemes:79,98,109`、`clause/edit:166,171,190`、`actuarial-workbench:213`、`template-config:243,247,250`。
- 这些字段均为 `:max="1"`。已实读 `node_modules/element-plus/es/components/input-number/src/input-number.vue_vue_type_script_setup_true_lang.mjs:138-141` 确认钳制逻辑：
  ```js
  if (newVal > max || newVal < min) {
      newVal = newVal > max ? max : min;   // 无任何报错、无提示
      update && emit("update:modelValue", newVal);
  }
  ```
- **后果**：用户在理赔模块学会「比例填 80」，切到渠道模块把佣金比例填 80 → 被**静默改写为 1（=100%）**，界面无任何提示，随后提交 → **写入 100% 佣金率**。`actuarial-workbench:213` 税率填 100 → 变 1 = **100% 税率**（客户应付翻倍）。

**② 输入用小数、展示用百分数，同一字段两个单位，用户无法建立映射。**

- `channel/list` 列表 `:49` 显示 `10.00%`，编辑弹窗 `:113` 输入框显示 `0.1` —— 同一字段、同一页面、两个量纲。
- `commission-schemes` 列表 `:168` 显示 `10%`，创建表单 `:79` 输入 `0.1`。
- `actuarial-workbench` 列表 `:119` 显示 `6%`（`percentText` ×100），创建抽屉 `:213` 输入 `0.06`。
- 用户只能靠「猜」知道 `0.1` 就是 `10%`，因为**输入框本身不带 `%` 后缀**。

**③ 「预览计算结果」零实现。**

- `src/api/pricing.ts` 全文件无任何 quote/试算端点绑定（`grep "quote\|Quote"` 零命中），而后端存在 `PremiumQuoteCommand`/`PremiumQuoteApplicationService`。
- 全站唯一的「看到算出来的保费」的路径是定价包的**发布门禁测试**（`pricing-plans:398-404`），它是**事后闸口**而非预览：需 APPROVED 状态、需先保存用例，且新用例 `expectedPremium` 默认 `0`、`tolerance` 默认 `0.01`（`:372`）→ **首次运行必然失败**，用户只能从失败结果里抄 `actualPremium` 回填预期值，反复试错。

## 三、分级发现明细

### 三.A BLOCKER（5 项）

#### B1 — 加费比例展示低估 100 倍（核保详情）

**证据**

- 前端展示：`src/views/underwriting/detail/index.vue:39-40`
  ```vue
  <el-descriptions-item v-if="detail.premiumSurchargeRate != null" label="加费比例">
    {{ Number(detail.premiumSurchargeRate).toLocaleString() }}%
  </el-descriptions-item>
  ```
  直接对 0-1 小数追加 `%`，**未 ×100**。后端返回 `0.30` → 界面显示 **"0.3%"**。
- 后端契约（权威）：`titanium-underwriting/titanium-underwriting-api/src/main/java/com/titanium/underwriting/api/response/underwriting/UnderwritingResponse.java:80-81`
  ```java
  @Schema(description = "加费率（比例加费时用，如 0.30 表示加费30%）", example = "0.30")
  private BigDecimal extraPremiumRatio;
  ```
- 字段映射链：`src/views/underwriting/web/mapper/UnderwritingWebMapper.java:49`
  `@Mapping(target = "premiumSurchargeRate", source = "extraPremiumRatio")` —— 确认前端接收的正是该比例值。
- 前端类型注释**错误**：`src/api/underwriting.ts:41-42`
  ```ts
  /** 保费加费比例（%） */
  premiumSurchargeRate?: number
  ```
  注释声称「（%）」诱导后来者沿用错误单位。

**影响**：核保员看到「加费比例 0.3%」，实际是「加费 30%」。核保结论复核、加费金额对账、客户告知书金额解释全部失真；若据此在保全/批改环节手工录入金额，会按 0.3% 而非 30% 计费，**资金差错 100 倍**。

**改法**
1. 展示统一走格式化函数（见 §四 批次 0）：`` `${(v * 100).toFixed(2)}%` ``，与本仓 `pct()` 约定一致（`product/detail:306`）。
2. 修正 `src/api/underwriting.ts:41` 注释为 `/** 保费加费比例（0-1 小数，0.30 表示加费 30%） */`。
3. 建议后端 `@Schema` 与前端类型注释双向标注同一约定，避免再次漂移。

#### B2 — 保全字段变更使用裸文本输入，金额/保额无类型约束

**证据**

- `src/views/maintenance/workbench/index.vue:46-50` —— 所有拟变更字段共用同一个渲染分支：
  ```vue
  <template #default="{ row }">
    <el-input v-model="draftValues[changeKey(row)]" size="small" :disabled="isReadOnly" :placeholder="row.proposedValue || '请输入'" />
  </template>
  ```
- `:265` `const draftValues = reactive<Record<string, string>>({})` —— **全字符串存储**，无 number 分支。
- `:302` / `:315` 已计算出类型：`dataType: rule.expectedValueType || 'TEXT'`，但模板中**从未使用** `row.dataType` 做分支。
- `:471` 提交时直接送字符串：
  ```js
  list.push({ objectId: row.objectId || null, fieldCode: row.fieldCode, dataType: row.dataType || 'TEXT', canonicalValue: draftValues[changeKey(row)] || null })
  ```
- `:496` 冲突重新录入同样走 `ElMessageBox.prompt` 纯文本。

**影响**：保额调整、保费调整、缴费年限等**高价值数值字段**，录入端可以输入 `"十万"`、`"10万"`、`"1O00"`（字母 O）、`"１０００"`（全角）、`"1000元"`；无千分位、无精度、无范围、无单位提示。由于 `dataType` 已在手，等于**类型信息被丢弃**。数据以字符串进入 `canonicalValue`，后端解析失败即为运行期错误，用户无法在提交前发现。

**改法**
1. 模板按 `row.dataType` 分支：
   ```vue
   <el-input-number v-if="['NUMBER','DECIMAL','AMOUNT'].includes(row.dataType)"
     v-model="draftValues[changeKey(row)]" :precision="precisionOf(row)" :min="minOf(row)" :max="maxOf(row)" size="small" :disabled="isReadOnly" />
   <el-input v-else v-model="draftValues[changeKey(row)]" ... />
   ```
2. `draftValues` 类型放宽为 `Record<string, string | number | null>`，提交时按 `dataType` 规整。
3. 为保额/保费类字段的 label 追加单位后缀（元），并在单元格下方以 `field-tip` 展示变更前值对比（`row.currentValue → 拟变更值`）。

5. 建议加「费率合理性软警告」：提交时若 `SUM_INSURED_RATIO` 且 `rate > 1`（即 >100%），弹确认框。

#### B5 — 保单资金操作使用无校验的 `ElMessageBox.prompt`

**证据**（`src/views/policy/detail/index.vue`）

- 红利派发 `:314-321`
  ```js
  case 'dividend':
    await ElMessageBox.prompt('请输入本年度红利金额（元）', '红利派发', { inputType: 'number' }).then(({ value }) =>
      doAction(() => distributeDividend(policy.value!.policyId, {
        policyYear: new Date().getFullYear(),

        option: 'ACCUMULATE',
      })),
    )
  ```
- 启动年金给付 `:322-330`：同样 `ElMessageBox.prompt`，`amountPerInstallment: Number(value)`，且 `:328` **硬编码 `currency: 'CNY'`**。
- 满期给付 `:332-340`：同样 `ElMessageBox.prompt`，`maturityBenefit: Number(value)`。

**缺陷点**

1. **无 `inputValidator`**：三个 prompt 均未传校验器。`Number('')` → `0`，空输入提交后是**金额 0** 的红利/年金/满期给付。`Number('abc')` → `NaN`，会作为 `NaN` 进入请求体。
2. **无精度与范围**：`inputType: 'number'` 仅影响键盘，不阻止 `1234.5678`、`-100`、`1e9`。
3. **币种硬编码**：`:328` 写死 `'CNY'`，但 `src/api/policy.ts:21` 保单上有 `currency?: string`，且 `src/api/policy.ts:144-149` `startAnnuityPayout` 的参数类型已接受 `currency?: string` —— **接口留了门，调用方把门钉死了**。美元/港币保单的年金给付会被记为人民币。
4. **无影响面确认**：这三笔都是**对外资金给付**，弹窗中不展示保单号、被保险人、当前保额等上下文，也不提示「此操作将产生给付流水」。

**影响**：空值静默变 0（给付漏发且无日志异常）、币种错配（跨币种保单资金记错科目）、无上限输入（`1e12` 可提交）。这类操作**不可逆**（给付一旦执行需走冲正）。

**改法**
```js
const { value } = await ElMessageBox.prompt('请输入本年度红利金额', '红利派发', {
  inputType: 'number',
  inputPlaceholder: `币种 ${policy.value?.currency ?? 'CNY'}，例：1000.00`,
  inputValidator: (v) => {
    const n = Number(v)
    if (!v || !Number.isFinite(n)) return '请输入有效金额'
    if (n <= 0) return '金额必须大于 0'
    if (Math.round(n * 100) !== n * 100) return '最多两位小数'
    return true
  },
})
```
1. 币种改为 `policy.value?.currency ?? 'CNY'`。
2. 弹窗标题/正文带上保单号与被保险人，降低「操作错对象」概率。
3. 更优：将三处 prompt 替换为一个共享的 `<MoneyInputDialog>` 组件（`el-input-number :precision="2" :min="0.01"` + 币种后缀 + 上下文摘要行），并复用 `formatAmount` 做只读确认预览（「本次给付：CNY 1,000.00」）。

#### W11 — 精算工作台：单控件同时承载金额与比例两种语义

**证据**（`src/views/product/actuarial-workbench/index.vue:287`）
```vue
<el-input-number v-if="['FIXED_AMOUNT', 'PERCENTAGE_OF'].includes(row.operator)" v-model="row.parameterValue" :min="0" :precision="6" ...>
```
- `FIXED_AMOUNT`：值是**金额**（元）。
- `PERCENTAGE_OF`：值是**比例**（0-1 小数，6 位精度）。
- 同一控件、同一字段、同一精度、**无任何单位提示与后缀**，语义完全由另一个下拉（operator）决定。

**改法**：`:287` 的控件按 operator 分支渲染：

```vue
<el-input-number v-if="row.operator === 'FIXED_AMOUNT'" v-model="row.parameterValue" :min="0" :precision="2" />       <!-- 后缀：元 -->
<el-input-number v-else-if="row.operator === 'PERCENTAGE_OF'" v-model="row.parameterValue" :min="0" :max="1" :precision="6" />  <!-- 后缀：实时百分数 -->
```

## 四、改造批次排序

### 4.0 前置问题：「统一格式化工具」是否需要先建？

**结论：需要，但它不是任何 BLOCKER 的阻塞项 —— 应并行启动，且必须控制在极小范围内。**

理由分三层：

1. **对 BLOCKER 无阻塞**。B1（`underwriting/detail:40` 缺 ×100）用一行修改即可修复，不必等工具；B2（保全裸输入）需要的是控件切换逻辑，不是格式化；B5（`ElMessageBox.prompt`）需要的是 `inputValidator`。**若先花两批做工具基建，5 个 BLOCKER 会带病存活数周**，而它们是会产生错误资金的。
2. **对 WARNING 有强杠杆**。W2（8 套比例格式化器）、W3（57 处缺币种）、W8/W15（表格裸值）本质是同一个根因：**没有权威实现，所以每个页面都自己写一份**。这三项合计约 70+ 处修改点，若不先集中工具，会在每个页面重复一次微小决策（精度几位？裁不裁尾零？），产出第 9、10 套实现。
3. **但工具本身必须极小**。参考现状：`src/utils/format.ts` 只有 45 行、单一函数 `formatAmount`。新增工具应**只加 3 个函数**（见下），不得借此引入 `Money` 类、`BigNumber` 依赖或配置化的 format 注册表 —— 那会超出「让页面不再各写一份」的实际需要（YAGNI）。

**建议新增（`src/utils/format.ts` 扩展，约 +40 行）**：

```ts
// 比例：0-1 小数 → 百分数文本；percentDigits 默认 2，trimZeros 默认 true
export function formatRate(value: number | string | null | undefined,
                           opts?: { percentDigits?: number; trimZeros?: boolean }): string

// 输入框后缀用：0.1 → "= 10%"，供 el-input-number 的 #suffix 插槽
export function formatRateHint(decimal?: number | null): string

// 百分数输入（0-100）→ 0-1 小数，提交层唯一转换点
export function percentToDecimal(percent: number | string | null | undefined): number | undefined
```

同时**修正 `formatAmount` 的调用规范**（函数本身不改，`src/utils/format.ts:22-23` 的注释已正确声明「只用于金额」）：新增 ESLint 或 Code Review 检查项，要求单参调用必须能说明无币种上下文的理由。

> 注：`src/utils/format.ts:22-23` 现有注释「费率另有各自的展示约定，见各页 `rateText`」—— 这句话在本次审计后应被视为**需要修订**：8 套 `rateText` 并非「约定」，是漂移。工具补齐后该注释应改为指向 `formatRate`。
